# Architecture

```
┌────────────────────────── Jaffer.app (Electron) ───────────────────────────┐
│ main process: window, menu, menu bar item, dock, notifications, hotkey,     │
│               updates, the quit question, IPC relay, the first-start clean-up│
│ renderer: Preact + xterm.js (WebGL) · command blocks · title bar · companion │
└───────────────▲───────────────────────────────────────┬─────────────────────┘
                │ unix socket (NDJSON RPC + events),    │ starts it as its CHILD (JAFFER_OWNED=1,
                │ ~/.jaffer/run/jafferd.sock            │ a pipe on its stdin: the pipe ends = stop)
┌───────────────┴──────────── jafferd (the app's child) ▼─────────────────────┐
│ SessionHost ── up to 4 × PtySession ── node-pty ── your login shells        │
│     │             └ one headless xterm each: snapshots, OSC 133/633 parsing  │
│ ClaudeWatcher ── live state of the terminal's Claude, from its hook events   │
│ cost reader · past conversations · git status · transcript watch · StayAwake│
│ pending permission requests (opt-in, at most 5, a redacted line each)       │
└───────────────▲─────────────────────────────────────────────────────────────┘
                │ same RPC
   jaffer CLI ──┴── `jaffer hook <event>` (run by Claude Code, inside Jaffer's terminal only)
```

There is one process tree and it has one owner: the app. Quitting the app ends every shell and anything running in them.

## The app owns the session

The terminal host, `jafferd`, is a separate process (the PTY and the headless terminal stay off the Electron main thread, and the hooks and the CLI reach it over a socket), but it is the app's **child**, not a background service. `startOwnedDaemon` (`src/core/daemon-client.ts`) spawns it with the app's own binary as `ELECTRON_RUN_AS_NODE=1` (no separate Node install), not detached, with `JAFFER_OWNED=1`, `JAFFER_HOME`, `JAFFER_CLI_SCRIPT` and a pipe on its stdin that the app holds and never writes; its stdout and stderr go to `~/.jaffer/run/jafferd.log` (rotated at 5 MB).

- **How it ends.** The daemon reads `JAFFER_OWNED` and deletes it from its own environment at once (`src/daemon/main.ts`; `JAFFER_OWNED` is also stripped from what the shell gets, so nothing it starts sees it). Once it listens, `watchParent` (`src/daemon/shutdown.ts`) takes the end of its stdin, however it comes (the app quits, crashes or is SIGKILLed: the system closes the app's end of the pipe), as the cue to stop: the shell is let go, the socket removed, exit code 0. The flag is opt-in: the tests, `ensureDaemon` and the dev bridge start the daemon detached with `stdio: 'ignore'` (`detachedSpawnArgs` removes the flag from the environment), and such a daemon runs until `app.shutdown` or a signal.
- **Exit codes** (`src/daemon/shutdown.ts`): 0 for a deliberate end (`app.shutdown`, the end of the app's pipe), 143 for SIGTERM and 130 for SIGINT; anything else is a crash. SIGHUP is ignored. The first reason wins (a second signal, or one during `app.shutdown`, neither exits early nor turns 0 into 143), and a stop that hangs ends at an 8 s deadline.
- **Only its own child.** `startOwnedDaemon` connects to the socket only when `hello.pid` is the child's pid; if another daemon already holds the socket, the child finds it taken and exits 0, and the start fails fast instead of taking someone else's session. A child that does not answer in 12 s is killed and the start fails ("Jaffer could not start its terminal", then the app quits).
- **Quitting.** Every quit ends every terminal; only one asks first. The menu's **Quit Jaffer** (`⌘Q`) is a custom item (not Electron's stock quit role) that sets a flag and calls `app.quit()`; `before-quit` reads and clears that flag and asks (`shouldAskOnQuit` in `src/shared/quit-policy.ts`) only when the quit came from it and something would stop: Claude Code is working or waiting for the person (the hook state), or the running command is `claude`, or any command runs in **any** terminal (the shells' own marks: `pty.start` / `pty.command` per pane, and `pane.list`'s `busy` at connect; main keeps `runningCommands`, one entry per pane, and `quitState` turns them into the question). The question is *Quit Jaffer?* with *Claude Code is running and will stop.* or *A command is running and will stop.*, **Quit** / **Cancel**; the default button is Cancel and Esc cancels. The window is brought forward first and the question is a sheet on it, so a window that is hidden does not leave it behind other apps. The menu bar item's **Quit Jaffer** is the same custom item and asks the same way. A quit the system starts (a logout, restart or shutdown, an AppleScript `quit`, the Dock's **Quit**) never asks: macOS takes a question at logout as the app refusing to quit and cancels the logout, so those end the shell and Claude Code without a question (the trade-off: Dock → Quit stops a running Claude Code unasked). Nothing is asked either for an update (its own prompt said so), Reset, a terminal that has already ended, or when nothing runs; a shell without Jaffer's marks (`/bin/sh`) or a background job is not seen. Then `will-quit` calls `OwnedDaemon.stop(3 s)`: the pipe is ended, the child gets 3 s, then SIGKILL, then the app exits. Closing the window is not quitting: the ✕ and `⌘W` hide it by default (*The menu bar item and closing the window*, below).
- **The child ends by itself** (`childExitAction`): exit 0 on its own is a session a client ended on purpose (`jaffer reset`, `jaffer daemon stop`): the app quits with it, without a question. Anything else is a crash: the window says *The terminal stopped.* and a native dialog offers **Restart terminal** (a fresh child, a fresh shell; the window re-attaches on `daemon.up`) or **Quit**. If the connection closes while the child still runs, the app waits 1 s for its exit, reconnects to the same pid for up to 5 s, and kills the child if it cannot be reached (which ends in the crash dialog).
- **Only the first instance runs.** `requestSingleInstanceLock`: a second app (opened from a disk image while the installed copy runs, `open -n`) calls `app.exit(0)` at once and starts nothing (the whole start is behind `gotLock`: it would find the first instance's own terminal on the socket and offer to end it); the first instance brings its window forward, once its start has made one.

### The start, in order (`whenReady`, `src/main/main.ts`)

1. The single-instance lock (above), then the menu.
2. **An older Jaffer's background session.** Before 0.6.0 the daemon outlived the app; after installing over a running one it may still hold the socket. When something answers there, the start first waits up to 3 s (`waitForSocketGone`) for a session that is already ending by itself (an update from an older version has just stopped it) and goes on without a question if it goes. If something still answers (`legacyDaemonAction`), a native dialog asks once: *Another Jaffer session is running in the background. Jaffer no longer keeps sessions running. End it and start a fresh terminal?* **End it** / **Quit** (the default button is Quit and Esc means Quit: nothing ends unless End it is clicked). End it sends `app.shutdown` (every older version knows it) and waits up to 10 s for the socket to go; if it stays, an error says to quit the other Jaffer process in Activity Monitor or restart the Mac, and the app quits.
3. **`prepareHome`** (`src/main/prepare-home.ts`): the first-start clean-up of an upgraded Mac (below), never throwing and bounded at 30 s.
4. **The terminal**: `startOwnedDaemon`, connect, read the settings (the hotkey).
5. The window, the Dock's `activate`, the updater, and under `JAFFER_SMOKE=1` the smoke test (which also checks that `hello.pid` is the app's own child).

## Terminals: up to four, only by a split

`SessionHost` (`src/core/session/host.ts`) holds up to four panes: `main`, `p2`, `p3`, `p4` (`IDS`; a free id is reused after a close). Each is a `PtySession` with its own login shell, headless terminal, snapshot sequence and respawn backoff, and its shell gets `JAFFER_PANE=<id>` (the daemon's own environment never has it). The daemon opens a pane only for `pane.split {pane?, cwd?, cols?, rows?}`: the folder is the `cwd` asked for when it is an existing directory, else the split pane's own, and the fifth is refused ("At most four terminals."). It ends a pane only for `pane.close {pane}` (the pane must be named; the last one is refused: `session.restart {pane}` gives it a fresh shell). A request without a `pane` means the first pane left (`main`), and `session.detach` without one detaches every pane (a 1.3 window's meaning). Nothing else creates a pane: there is no restore, no CLI command and nothing a hook can do; in the window only `⌘D` (the Shell menu, the palette, the tour's *Try it*) splits.

**Nothing of any terminal is saved or replayed, and neither is the layout.** A start has one terminal in the home folder with a blank screen. If a shell exits (`exit`, a crash, *Restart shell*) the host starts a fresh one in the folder the old one was in, with a blank screen, after a short wait that doubles (up to 10 s) while that pane's shells die within seconds of starting; a pane the person closed (`lifecycle: 'closed'`) is not respawned. The window is told to start over from the new shell's blank screen (a `pty.reset` to every client attached to that pane, `resyncAttached`), because the new shell's output counts from 1 again. 0.5.x saved the screen and replayed it into the new shell, which could replay a dead program's terminal modes (mouse reporting) into a fresh shell; with the saved screen gone, that is gone too.

Per pane, in the daemon: the attach state of each connection (a set of panes, `attachedTo(pane)`; `session.lifecycle` goes to connections attached to any pane, and after `closed` every set has forgotten the pane, so a reused id needs a fresh `session.attach`), the output backpressure and `pty.reset` (a connection that falls behind on one pane is resynced on that pane only, and not if it has detached meanwhile), the git status and its timer, the running command, and the Claude session (the hook CLI forwards `JAFFER_PANE` as `jaffer_pane`, `ClaudeSession.pane`; a pane's shell exiting or its `claude` command ending calls `endPane(pane)`, which ends that pane's sessions and those with no known pane, and `userAnswered(pane)` moves only that pane's needs-you sessions). Staying awake counts a command in any alive pane: `pickCommand` (`stay-awake.ts`, pure) takes the oldest non-interactive command under the 6 h cap, then ones past the cap, then interactive ones, so `less` in one terminal does not hide a build in another.

**In the window** (`state.ts`, `components/PaneTree.tsx`, `TerminalView.tsx`): `panes` is the ids in the order opened, `paneInfo` the info of each, and `info` a `computed` that is the focused pane's, so every older consumer (the title bar, the folder, the badge) follows the focus. `paneGrid(count)` (`src/shared/pane-grid.ts`) is the geometry: one fills the card, two sit side by side, three are one on the left spanning both rows and two stacked on the right, four are two by two, all equal, no dragging. Each `.pane` is keyed by its id and a generation (an id reused after a close remounts and re-attaches), holds its own `TerminalView` (it fits itself and sends its own `pty.resize`; every RPC to a terminal names its pane) and a small chip `.pn-chip`: a dot while that pane's Claude has not ended, the folder's base name and a ✕. The ✕ calls `pane.close`, or on the last pane `session.restart` (*Restart terminal*); when a command or a Claude runs there it first shows `.pn-confirm` under the chip (*A command is running: <safeCommand>* / *Claude is running here*, *End terminal*, *Cancel*; Cancel has the focus and Esc cancels), and `closeAsk` (memory) holds the open question and is cleared when that pane goes. `splitTerminal`, `closeTerminal`, `focusTerminal(n)` and `cycleTerminal(±1)` are the actions behind the menu and the palette (`split-terminal` ⌘D, `close-terminal` ⇧⌘W, `focus-terminal-1..4` ⌘1..⌘4, `next-terminal` ⌘], `prev-terminal` ⌘[, all in `menu-spec.ts`). The command blocks, the sticky header, the find bar, the paste bar (it carries its pane) and the port chip act on the focused pane; every pane's turns are tracked (a summary or compacting toast from a terminal that is not focused is prefixed with its folder). The window's `currentClaude()` prefers the focused pane's Claude, else the first one that has not ended. `resumeConversation` types only into the focused pane and only when that pane's own marks say it is idle.

## Terminal fidelity and re-attach

PTY output is parsed by a headless xterm.js in the daemon *before* it is emitted to clients. A client attaches with `session.attach`, which waits for the write queue to drain and returns `serialize()` output (screen + scrollback + alt-screen + modes) plus a sequence number; every later `pty.data` event carries `seq`, so the renderer drops anything already covered by the snapshot and re-attaches on any gap (the window re-attaches when its page reloads, for instance). Slow clients are resynchronised from a snapshot (`pty.reset`) instead of buffering without bound.

Shell integration scripts (`resources/shell`, embedded into `src/generated`) hook zsh (`ZDOTDIR` shim that sources your real dotfiles), bash (`--init-file`, bash 3.2 compatible) and fish. They emit OSC 133 (`A` prompt, `C` output start, `D;<exit>`) and OSC 633 (`E` command line, `P;Cwd=`). From those the daemon knows what ran, with what exit code, for how long and in which folder (`pty.start`, `pty.command`, `pty.cwd`); the title bar, the notifications, the quit question and staying awake follow them. The marks are output, and any program can print them, so nothing that matters rests on them alone, and the command line they carry is read only by helpers that cut it to a head (see *Process boundaries and trust*): the daemon keeps at most `4 * COMMAND_HEAD` characters of a `633;E` command and of a `633;P;Cwd`. The window reads the same marks again, on its own xterm parser (*Command blocks*, below). The shell gets `JAFFER_SESSION=1` (which switches the hooks on), `JAFFER_PANE` (1.4.0: the terminal's id), `JAFFER_HOME`, `JAFFER_SOCK`, `JAFFER_BIN` (the integration scripts put it on the `PATH`, so `jaffer` works) and `TERM_PROGRAM=Jaffer`.

**The daemon types nothing of its own into any shell.** Only what the window sends (`pty.write`: the person's keys and the terminal's own replies, always naming a pane) reaches it. The product types two things, and the window does it, through its terminal, as the person would: `claude` (⇧⌘C, *Run Claude Code*, and the first-run switch *Start Claude Code in the terminal now*) and, since 1.1.1, the resume line of a past conversation, only after the person's own action and only at an idle prompt of the focused terminal (since 1.4.0, and only with `permissions.resumeTyping` on: off, it is copied): a click or Enter on a row of the side panel, Enter on a conversation in the command palette and ⇧⌘R, *Resume Last Conversation* (the last two since 1.2.0). All of them go through `resumeConversation` (*Past conversations*, below). Claude Code's own questions (trust a folder, allow a tool) stay in the terminal and Jaffer answers none of them.

## One Claude, and a quiet reflection of it

There is one Claude in Jaffer: the `claude` running in the terminal. Jaffer has no chat of its own and runs no model of its own. The mole (or another scene), the title-bar ring, the side panel's Now card and a desktop notification reflect what Claude Code is doing, fed by Claude Code's own hooks. There is no chat.

- **Events in.** *Settings → Claude Code → Connect*, the first-run consent and `jaffer setup claude` register hooks in `~/.claude/settings.json` (and a daemon start refreshes them when they already point at its own wrapper): SessionStart, Stop, UserPromptSubmit, PreToolUse, PostToolUse, PostToolUseFailure, SubagentStart, SubagentStop, Notification, SessionEnd and PreCompact (the eleventh, new in 1.0.0: a daemon start reinstalls Jaffer's own entries when they already point at its wrapper, so an install of the ten gets it at the first start; `HOOK_EVENTS` in `src/core/integrations/claude.ts` is the list). A twelfth, `PermissionRequest`, exists only while `claude.approvals` is on and is the one that is *not* async (*Permission prompts from the notification*, below). All eleven are `async` (Claude Code never waits for them, five seconds at most), guarded by `[ "$JAFFER_SESSION" = 1 ] || exit 0` so they do not even start Jaffer outside its terminal, and tagged `# jaffer-managed` so that only Jaffer's own entries are ever changed or removed. Each runs `jaffer hook <event>` (through `~/.jaffer/bin/jaffer`), which does nothing unless `JAFFER_SESSION=1`, adds `jaffer_pane` (from `JAFFER_PANE`, only when it passes `isPaneId`; one the payload carried is deleted first) and forwards the JSON payload to the daemon as `claude.event`, prints nothing and exits 0 on every path, so Claude Code behaves exactly as without Jaffer when the daemon is down or slow. A `claude` that the daemon runs itself (`claude auth ...`) has `JAFFER_NO_HOOKS=1` and reports nothing.
- **State.** `ClaudeWatcher` (`src/core/claude/watcher.ts`) is a pure state machine per `session_id`: `idle`, `working`, `needs-you` or `ended`, the tool call being run (its name and id, never its arguments), background agents (id, running or done, when they started, and the name of the tool each is running when the payload carries its `agent_id`), Claude Code's own permission wording (`notice`, redacted) and the cost of the answers. Since 1.0.0 it also keeps, **in the daemon's memory and for the session only**: `calls` (this session's tool calls, the last 200: name, category from `toolCategory`, start, end, failed, agent id), `counts` per category since the last prompt (all calls, also those `calls` let go), `file` (the file the running `Edit`, `Write`, `MultiEdit` or `NotebookEdit` writes) and `files` (the files those wrote since the last prompt, each once, at most 50, a file only after a call that succeeded), `pane` (1.4.0: the terminal the hooks ran in, a short plain id; invalid ones ignored), `context` (1.4.0: `{tokens, window?, at}`, numbers only; cleared by `PreCompact`), `startedAt` and `turns` (the session clock), `turnStartedAt` and `compacting` (set by `PreCompact`, cleared by the next `SessionStart` with `source: compact`, a prompt, a tool call, `Stop` or the session's end, or after five quiet minutes by the sweep). A path is kept only when it is at most 1024 characters, `isSensitivePath` does not flag it (keys, credentials, `.env*`, `.ssh/`, `.kube/config`, ... ; past 4096 characters it fails closed) and it passes `redactText`. It still keeps **no prompt, command, reply, folder, other tool argument or agent description**: a test drives secrets through every payload field and pins the exact keys that leave the daemon. Hooks are asynchronous and can arrive out of order, so only UserPromptSubmit and PreToolUse move a session to `working`, a SessionStart that lands late never takes a working or waiting session back to idle, one that arrives within 3 s after its own session ended is that run's start arriving late and is ignored (unless Claude Code says the session goes on: source `resume`, `clear` or `compact`), a permission Notification only counts while a tool is pending, and the late result of an earlier overlapping call does not clear a later tool; a call is closed by its `tool_use_id` (kept only in the daemon), and a turn's end closes every call still open. `sessions()` is the daemon's own view (with the transcript path it reads and the call ids); `view()` is what leaves the daemon, over the `claude.state` RPC and event, and has neither (the edited files' paths are in it: redacted, never a sensitive one).
- **Staleness.** Declining a prompt or pressing Esc in the terminal fires no hook (and Esc no `Stop`), so while a session is `working` or `needs-you` the daemon reads the tail of its transcript (`transcript-watch.ts`) for the person's own "User rejected tool use" / "[Request interrupted by user" entry (`isStopLine`: the user side only, text starting with the marker, so the same words in code or command output do not count) and calls `ClaudeWatcher.interrupted`. A sweep every 30 s is the safety net for a turn that ended with no signal at all: `working` with no hook for 5 minutes (30 with a tool running) and a transcript that is not growing becomes idle; `needs-you` is never swept. The `claude` command finishing in the shell ends every session (also a crashed Claude Code), unless it was only stopped (Ctrl+Z), and so does the shell itself exiting.
- **Notifications** (the main process, only while the window is not in front): *Claude needs you* when a session newly enters `needs-you` (`notify-policy.ts`; the Dock icon bounces too), *Claude finished* after a turn of 30 s or more (`FinishedNotifier`: it waits up to 2.5 s for the cost of the answer, and stays quiet if the window came to the front, the next turn began, or Claude Code's own terminal notification just fired; `notifications.claudeFinished` turns it off), a command that ran 30 s or more (*Command finished* / *Command failed*, redacted, a sensitive command not named), and the terminal's own notifications (OSC 9 and 777). Claude Code's own terminal notification and Jaffer's never both fire for one event (a 10 s window). With the opt-in approvals on, a request also gets *Claude asks to use <tool>* with Show, Deny and (when the request is shown whole) Allow (*Permission prompts from the notification*, below). *Claude needs you* and *Claude finished* carry a **Show** button (`actions` on the `Notification`), and both the click and the button show the window, also a hidden one (macOS may list the button only under *Options*, depending on the person's notification style). In **focus mode** (⌥⌘F; see *Focus mode*) these are held and counted instead.
- **Cost.** When `claude.showCost` is on, the daemon notes the size of the transcript at `UserPromptSubmit` and, at `Stop`, reads what was written since (`core/claude/cost.ts`, up to the end it measured, so a response Claude gives later without a prompt is measured from there; where a turn began is kept 10 s past the session's end, because the Stop of a `claude -p` answer can arrive after its SessionEnd). `shared/claude-cost.ts` sums the `usage` of each model response once per message id (Claude Code writes one line per content block, all carrying the same usage) and prices it from a table of Anthropic's list prices (cache reads and 5-minute and 1-hour cache writes separately; fast mode and US-only inference where the model has them). A model id the table does not know exactly (a dated snapshot is fine, `claude-opus-5-6` is not `claude-opus-5`) gets tokens and no dollars, never the nearest price. Only numbers are kept: `ClaudeSession.cost` holds the last answer's tokens and dollars and the session total, in the daemon's memory for as long as the session lives; no text from the transcript reaches the state or the UI. Background agents' own usage is not in the main transcript's totals. The title bar shows it (`CostChip`); the price table is the one thing to update when Anthropic changes prices or adds a model. Since 1.0.0 the daemon also (a) reads the same transcript every 2 s **while a turn works** (`claude.liveCost` and `showCost` on; only when the file grew; the same bounded reader) and puts `live: {input, output, usd?}` on the session, so the chip can show a greyed *≈ $0.03 so far*; (b) adds each finished answer to **today's total** (`DayTotal` in `shared/claude-cost.ts`: memory only, local `YYYY-MM-DD`, starts again at midnight by the 30 s sweep, and a `Stop` heard twice counts once), sent as `today` next to `sessions` in `claude.state`; and (b2) since 1.2.0 adds the length of each finished turn (a `Stop` of a working or waiting turn, once) to `DayTotal.workMs`, the time Claude worked today (memory only, like the cost; resets at midnight and with the daemon; turns under 1 s are ignored; a turn that ends by Esc or a declined prompt fires no `Stop`, so it is not counted: the figure undercounts), shown as "Claude worked 1h 12m today" (the running turn is added by the window); and (c) keeps the median length of the last 15 turns of 3 s or more (`turn-median.ts`) and stores it in `claude.typicalTurnMs`, the ring's reference. `claude.dailyBudgetUsd` (0 = off) only colours the chip (`warn` from 80 %, `danger` from 100 %); nothing is blocked.
- **Sign-in help.** `claudeAuth` asks `claude auth status --json` (only the logged-in flag is read; the account stays inside that function) and `ClaudeLogin` runs `claude auth login`, which opens the browser. Both run with the person's own environment minus `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN`: Jaffer runs on Claude subscriptions only. `findClaude` finds the binary the way the person's shell would (PATH, the usual install folders, then the login shell, 8 s at most). Claude is optional: the first-run step *Use Jaffer as a plain terminal for now* installs nothing and starts nothing and sets `claude.skipped`; connecting clears it.
- **Surface.** RPC `claude.event` (from hooks), `claude.state` (snapshot: `{ sessions, today }`), `claude.hooks` (`{ events }`: for each of the eleven events when the daemon last saw one, or `null`; memory only, since the app started; Settings → Claude Code shows it) and the pushed event `claude.state` (throttled to one per 100 ms). The daemon also answers `claude.history` (below), since 1.4.0 `pane.split`, `pane.close`, `claude.usage5h`, `claude.storage`, `claude.old`, `claude.search`, `claude.setup`, `claude.mcp`, `claude.explain` and `claude.explain.supported` (the sections below), and, since 1.2.0, `claude.approval` (from the blocking hook), `claude.approval.answer` and `claude.approvals` (the pending list) and pushes the event `claude.approvals`. The state lives in the daemon, which lives as long as the app.
- **Data flow.** Claude Code runs `jaffer hook <event>` → the daemon's `claude.event` → `ClaudeWatcher` fills its fields → `view()` → the `claude.state` event → main (notifications and the Dock read `sessions`; `FocusHold` may hold them) and the renderer (`setClaude` in `state.ts`: the signals `claudeLive`, `claudeToday`, `turnHistory`, `turnDone`; the toasts for compacting and for a finished turn) → the title bar (`Chrome.tsx`), the tool strip, the glow and the companion. The renderer tolerates a payload without any of the new fields (older state, tests).
- **Not built:** diffs from the transcript.

## Permission prompts from the notification (1.2.0, opt-in)

`claude.approvals` (Settings → Privacy and permissions since 1.4.0, off by default) lets the person answer a Claude Code permission prompt with a click. It is the one place where a hook is not asynchronous, so it is built to fail silent.

- **The hook.** While the setting is on and Jaffer's hooks point at its wrapper, `installHooks(cli, home, { approvals })` adds `PermissionRequest` → `[ "$JAFFER_SESSION" = 1 ] || exit 0; '<cli>' hook permission-request # jaffer-managed`, with `timeout: 25` (longer than the 20 s wait) and no `async` key. Turned off, the entry is removed, and the key with it when nothing of the person's is left; `removeHooks`, `teardownClaude`, Reset and `jaffer setup claude --remove` remove it too, and `jaffer setup claude` follows the setting. `HOOK_EVENTS` stays the eleven: the health list never reports the twelfth as missing.
- **The CLI** (`jaffer hook permission-request`) runs after the usual guards (`JAFFER_NO_HOOKS`, `JAFFER_SESSION=1`), reads at most 1 MB of stdin and destroys it (a stdin Claude Code keeps open must not hold the hook), connects with a 600 ms timeout, sends only `session_id`, `tool_name`, `tool_input` and `cwd` in `claude.approval` and waits up to `APPROVAL_WAIT_MS` (20 s) plus a second. It prints a decision **only** for `{ decision: 'allow' | 'deny' }`: exactly `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}}`, or the same with `"behavior":"deny","message":"Denied from Jaffer"` (`decisionOutput` in `src/core/claude/approvals.ts`; never `updatedInput`, `updatedPermissions` or `interrupt`). Any other answer, a timeout, no daemon, garbage on stdin or an error: no output, exit 0, so Claude Code shows its own prompt. Exit code 2 is never used.
- **The daemon** (`service.ts`) answers `claude.approval` with `{ decision: null }` at once when the setting is off, it is stopping, 5 requests already wait or no app connection exists (`hello { client: 'app' }` marks the window's connection). Otherwise it keeps a *view* in memory: a random id, the session, the tool name (`approvalTool`: redacted, hidden characters removed, at most 64), a one-line detail (`approvalDetail`) and `allowable`, with an expiry; `tool_input` is read for the detail and dropped, and the watcher never sees the payload. It pushes `claude.approvals { items, answered? }` and waits. A request ends (the hook gets `null`) on a timeout, when the app's last connection closes, when the hook's own connection closes, when the setting goes off or at shutdown. `claude.approval.answer { id, decision }` takes `'allow'`, `'deny'` or `'ask'` from an app connection only; `'ask'` releases the hook at once; `'allow'` returns `{ ok: false }` for a request that is not `allowable` and leaves it waiting; the first answer wins. `JAFFER_TEST_APPROVAL_WAIT_MS` can only shorten the wait.
- **The line** (`approvalDetail(tool, input, { cwd, home })` → `{ text, complete }`): Bash shows the command, the file tools the path (relative to `cwd`, else with `~`), `WebFetch` the URL; every other tool shows nothing. The input is clipped before it is read, a newline is shown as `⏎`, a run of hidden characters (control, bidi, zero-width, soft hyphen, fillers, tag characters) as one `�`, and past 120 characters or `COMMAND_HEAD` the text is the first 99 characters plus `… (+N chars)`. **`complete`**, and with it `allowable`, is false when redaction changed the text, it was cut, it held a newline or a hidden character, the command is sensitive (`isSensitiveCommand`: the text says so instead of the command), the path is sensitive (`isSensitivePath`: "a key or credential file"), or there is no line. So Allow is never offered for something the person cannot read whole.
- **The window.** `approvals` (a signal in `state.ts`) holds the list. `ApprovalAsk` (`Chrome.tsx`), keyed by request id, shows the tool, the detail and a countdown. In the Now card: **Deny**, **Allow** (only when `allowable`) and **Answer in terminal** (`ask`); in the title-bar chip: Deny and Answer in terminal, never Allow. Allow is dimmed and `aria-disabled` for 750 ms after that id first rendered (`ARM_MS`, so a double click or a click aimed at something that just vanished cannot allow the next request) and then acts only on a click that is `isTrusted` with `detail === 1`; it has `tabIndex={-1}` and no key binding, so the keyboard, VoiceOver's activation and scripted clicks do nothing. A request that is not allowable shows why. An answer counts in `timesAnswered`.
- **The notification** (`onApprovals` in `main.ts`) is made once per id, only while the window is not focused and focus mode does not hold it, titled *Claude asks to use <tool>* with the detail as its body and the buttons **Show**, **Deny** and (only when `allowable`) **Allow**, in that order. Index 1 answers deny, index 2 answers allow, anything else (Show) answers `ask` and shows the window; a plain click only shows the window. Notifications of requests that are no longer pending are closed.
- **Trust.** The app-only check on `claude.approval.answer` is defense in depth: any process of the same user can say `hello { client: 'app' }` on the 0600 socket, exactly as it can send `pty.write` to type into the shell. What stands behind it is that Allow needs a trusted click in the window or on the notification, that an unreadable request cannot be allowed, and that every failure leaves Claude Code's own prompt.
- **What is inferred, not run.** Payload, output shape and the hook's timeout come from Claude Code's hook documentation; that the hook blocks before Claude Code draws its own dialog, and that silence falls back to it, are inferences (the README's *Not verified here*). That is why the setting is opt-in.

## Privacy and permissions (1.4.0)

`permissions.*` in `config.json` are five switches with `claude.approvals` (*Settings → Privacy and permissions* and the last first-run stage, `PrivacySwitches`): `explain` (off), `deepSearch` (off), `resumeTyping` (on), `trash` (on). Each says in plain words what it reads, sends or does. `resumeTyping` off turns every typed resume into a copy with a toast that says why (`resumeAction(..., { allowTyping })`, passed by `resumeConversation`). `trash` off makes main refuse every id with the reason `off` before it looks anything up or asks (`TrashDeps.enabled`, mirrored from the config) and hides the buttons. `deepSearch` and `explain` are checked by the daemon on every call, from its own config (`EPERM` / reason `off`). **Locked, no switch:** *Allow* needs the trusted, armed click and the whole request; Jaffer never reads Claude's login files (`~/.claude.json`, the keychain item); nothing is deleted for good; everything shown is redacted and a sensitive command is never named. **A switch is consent, not a boundary:** any process of the same user can `config.patch` it or call the daemon on the 0600 socket, as it can send `pty.write`; the checks keep the page, the daemon and main in agreement and promise no more.

## Claude insight (1.4.0)

All of it is numbers, in memory, and (except the week) derived from what the daemon already read.
- **Context meter.** At `Stop` (and in the live read) the daemon's cost reader also takes the latest non-sidechain response's input + cache-write + cache-read tokens and its model id (`summarizeTurn`, `readTurn`); `ClaudeWatcher.setContext` keeps `{tokens, window?, at}`, and `contextWindow(model)` (`src/shared/claude-cost.ts`) gives 1,000,000 for the families Anthropic's documentation of 2026-10-16 names as 1M, 200,000 for other `claude-*` ids and nothing for an unknown one (update it from the page, not from memory). With `claude.showCost` off the transcript is not read for this at all.
- **Last 5 hours** (`claude.usage5h`, `src/core/claude/usage-window.ts`): the tokens and priced dollars of response lines timestamped in the last five hours, from at most 60 transcripts modified in that window (confined like the history reader), each read backwards in 1 MB chunks (24 MB at most) until the first older response, yielding between chunks, with one in-flight scan shared by overlapping calls and message ids de-duplicated across files. It returns zeros while `claude.showCost` is off.
- **Week and digest** (`src/shared/usage-week.ts`): `usage` in `config.json` gets each counted turn's dollars (with `showCost`) and work time; `weekId` is the local ISO week and `rollWeek` moves a finished week to `lastWeek`. At the window's first load of an app run main's `weeklyDigest` asks `digestDue` for the week just past, writes `usage.digestWeek` first, then notifies (kind `digest`, which focus mode reports as "the weekly summary") and sends `app.digest` to the page for a toast with *Open panel*; `notifications.weeklyDigest` switches both off, and the dollars appear only with `showCost`.
- **Budgets.** `claude.dailyWorkBudgetMin` colours the worked line (80 % warn, 100 % danger) and toasts once a day. `claude.projectBudgets` (`parseProjectBudgets`, `budgetLevels`: absolute or `~` folders, dollars a week, the last `=` splits, at most 20, the last 7 days of that exact folder) tint the folder's row in *Cost by folder* and toast once per folder and ISO week; they count the 30 newest costed conversations only, a folder outside the five busiest has no row (its toast still comes), and nothing is stopped.
- **Toasts and tips.** The context toast (85 %, needs `showCost`) fires once per session id and again after a compaction.

## Past conversations: tags, hide, storage, clear old, deep search (1.4.0)

`history.tags` (`"<session id> <tag>"`, at most 3 per conversation, 400 in all, 20 characters, case-insensitive unique) and `history.hidden` (ids, at most 500) are the person's own words and ids (`src/shared/history-tags.ts`); filtering is `filterConversations` in `history-label.ts`. `claude.storage` (`conversationStorage`) sums `lstat` sizes of `<id>.jsonl` and its sibling real folder (links skipped, bounded walk, one shared in-flight promise, a 30 s cache) and returns the total, the count and the ten biggest (the folder and last time from the usual head/tail reader, a title only when already cached); each has a trash button into the existing removal path and its question. `claude.old {days: 30|60|90}` (`oldConversations`) returns ids by mtime, oldest first, at most 200 (`MAX_REMOVE`), and the counts for all three (one call when *Remove…* opens). **Deep search** (`claude.search`, `src/core/claude/search.ts`): needs `permissions.deepSearch` (checked per call, else `EPERM`), a query of 3 to 64 characters; it scans the 200 newest transcripts (confined like the history reader), the whole file up to 2 MB else its first and last 1 MB, and parses a line only when it can hold the query; only `user` and `assistant` lines' text (a string or `type: 'text'` parts), never `isMeta`, `isCompactSummary` or `isSidechain` lines or text starting with `<`, never tool inputs, results or thinking; a case-insensitive plain substring; the answer is ids and counts (at most 99 each), no snippet, a 5 s budget, a newer search cancels the older, nothing cached or logged. The counts are a substring oracle for any client of the socket (same user; defense in depth). The removal rule is unchanged: the only write to Claude Code's files, to the Trash, after a question.

## Staying awake

`StayAwake` (`src/core/session/stay-awake.ts`) is the decision (a command in any terminal counts, see *Terminals*), with its clock, timers and effects injected so the tests need no waiting; `caffeinate.ts` is the one place that touches the Mac: `/usr/bin/caffeinate -i -w <daemon pid>`. `-i` holds off idle system sleep only (never the display) and `-w` ends the hold by itself if the daemon dies (so a daemon that dies cannot leave one behind). The daemon hands it what works: a Claude session `working` or a background agent running, or a command that has run 30 s in a shell and is not an interactive program (`isInteractiveCommand`: `ssh`, `mosh`, `vim`, `less`, `man`, `top`, `tmux`, `watch`, `tail -f`, `claude`, ..., also behind `sudo`, `env`, `nice`, `time`, `nohup` and the like, with their options and the values those take, as in `sudo --user deploy vim`). A Claude that waits for the person (`needs-you`) is not work. The hold is let go 15 s after the work stops, so a pause between tool calls does not flap it; a command alone never holds longer than 6 hours. It releases at once when `session.stayAwake` goes off and when the daemon stops, and does nothing off macOS or for a home that is not the default one (`isDefaultHome`). There is one `caffeinate` at a time; if it ends by itself while the work goes on (killed, crashed, could not start: said once in the log), the hold is taken up again after 1 s, doubling at each end up to 30 s and starting over after a clean minute (`STAY_AWAKE` in `src/shared/stay-awake-config.ts`). It needs no admin rights and does not override the lid: `pmset disablesleep` is not used, and Jaffer never asks for a password. `JAFFER_TEST_HOLD_LOG=<file>` stands in for macOS in the tests (every hold and release is a line of JSON in the file), and `JAFFER_TEST_STAY_AWAKE_AFTER_MS` can only shorten the 30 s a command must run.

## The first start on a Mac an older Jaffer ran on

0.5.x kept a background session, a login agent, a saved screen and a memory. 0.6.0 kept none of them and takes away what they left, once; 1.0.0 does the same unchanged, so a Mac that goes from 0.5 or earlier straight to 1.0.0 gets it at its first start. `migrateToPlainTerminal` (`src/core/migrate.ts`, called by `prepareHome` after an older session has been ended and before the child starts) runs when `config.json` has no `migrated: 1`; every later start reads that one file and does nothing. In the order it runs, each step on its own:

1. `agent` — `removeLegacyAgent` (`src/core/service/legacy-agent.ts`): the login agent's plist (`~/Library/LaunchAgents/com.jafforge.jaffer.daemon.plist`), its wrapper (`~/.jaffer/bin/jafferd`) and its job in launchd (`launchctl bootout gui/<uid>/com.jafforge.jaffer.daemon`, 20 s at most, then SIGKILL; a job launchd does not know is the usual case). The reason it is first: an agent left behind would start a daemon of its own, or fail every five seconds if the app it names moved. The wrapper names `dist/daemon/jafferd.cjs`, which is why that file never moves. `JAFFER_NO_LAUNCHCTL=1` skips the `launchctl` call.
2. `backup` — `memory/NOTES.md` and `memory/POLICY.md` are copied to `~/.jaffer-memory-backup/` (a private 0700 folder, files 0600, never over something there: `NOTES-2.md`...) when they hold anything of the person's: a regular file, not blank, and a `POLICY.md` that is not still exactly the text every older version seeded.
3. `oldData` — `memory/`, `session/` and `bin/jafferd` are deleted (the memory only once its backup is made; if the backup failed it stays and the log says so). A link is removed, never followed.
4. `claudeMd`, `skills`, `firstDayBlocks` — Jaffer's marked block is taken out of `~/.claude/CLAUDE.md` (and, from the first builds, `~/.codex/AGENTS.md` and `~/.gemini/GEMINI.md`), everything else in the file byte for byte (a file that held only the block is deleted); and the `~/.claude/skills/jaffer-*` folders whose `SKILL.md` carries Jaffer's marker line (the person's own `jaffer-…` skills stay). The exact markers are in `src/core/integrations/legacy-claude.ts` and never change.
5. `config` — the settings 0.6.0 no longer has are pruned from `config.json` (`DEAD_KEYS`: `memory`, `ingest`, `export`, `safety`, `session.restoreScreen`, `session.resumeClaude`, `session.keepRunning`, `session.autoResume`; every other key, unknown ones included, stays) and `migrated: 1` is written, whatever the steps before did: a step that failed is not retried at every start. A `config.json` that cannot be read as settings is kept as `config.json.unreadable`. A start that was ended before this step (the app quit while `launchctl` was asked) has not set the marker and runs everything again; every step is safe to repeat.
6. `mcp` — `claude mcp remove jaffer -s user` (10 s at most; `claude` is looked for only now, only when an older Jaffer folder existed, so a fresh install runs no `claude`). It exits non-zero when no such server was registered, which the log records as `failed` with both readings.

The hooks are not touched here: the child rewrites Jaffer's own (`# jaffer-managed`) at its start when they already point at its wrapper, so a 0.5 install's SessionStart and Stop become async and silent.

- **Bounds and safety.** The whole thing gets 30 s (`prepareHomeBounded`) and never throws. A failing step is a line in `~/.jaffer/migrate.log` (the step's name and an error code or a few words, never a path) and the others still run; the log also says `started` first (so an interrupted start leaves a trace) and then has one summary line that lists every step's result, then one line per failed step. Nothing at all is done in a folder `assertJafferHome` does not accept (the home folder or a parent of it, the root, a code checkout, a folder without "jaffer" in its name, or one that holds files but none of Jaffer's own; links are resolved first: a `~/.jaffer` that is a link to the home folder is refused, and one that is a link must point at a folder named like Jaffer's).
- **Only for the person's own folder.** What lies outside `~/.jaffer` (steps `agent`, `claudeMd`, `skills`, `firstDayBlocks`, `mcp`) is touched only when the home is the default one (`isDefaultHome`, which also requires `$HOME` to be the system's home for the user): a smoke test or a dev run with another `JAFFER_HOME` cleans inside that folder and leaves the person's Claude Code files and launchd alone, with one exception: the backup of `NOTES.md` and `POLICY.md` is written to `~/.jaffer-memory-backup/` in the user's home whatever the Jaffer home (it only copies, and only when the home has such files of the person's). It still deletes `memory/`, `session/` and `bin/jafferd` inside the folder it was given: never point the app at a real `~/.jaffer` to look at it. That guard covers the clean-up only: a dev run with another `JAFFER_HOME` can still write hooks into the real `~/.claude/settings.json` (the first-run *Let Jaffer follow Claude Code*, *Settings → Claude Code → Connect*), pointing at that home's wrapper, and Reset (*Settings → Reset*, `jaffer reset`) removes the real hooks, MCP server, `CLAUDE.md` block and skills of Jaffer's whatever the home. Experiments use a throwaway `HOME` too, as the tests do.
- **Run it again** with `jaffer config set migrated 0`: the next start of the app repeats it.
- **Reset** (`src/core/reset.ts`, *Settings → Reset* and `jaffer reset`) runs the same cleanups on request and more: the login agent, then the session ends (`endSession`: the app stops its child; the CLI asks the daemon to `app.shutdown`), Jaffer's hooks (the person's own stay), the MCP server, the blocks and skills above, the `~/.local/bin/jaffer` link when it points into Jaffer's folder, the update cache, the app's own data (`jaffer reset` removes Electron's folders and preferences; the app's Reset clears its own storage and cache and the login item) and `~/.jaffer` itself, moved aside as `~/.jaffer.backup-<time>` unless the person chose to delete it; the app then relaunches as a fresh install. Claude Code itself, its login and the person's own settings stay. Reset judges the folder with `assertJafferHome` too; for a `~/.jaffer` that is a link it renames or removes only the link, never what it points at. `jaffer reset` refuses to run inside Jaffer's own session (it would end the terminal it was typed in); the app's Reset asks in its own dialog first.
- **The legacy modules** (`legacy-claude.ts`, `legacy-agent.ts`) are the only code that still knows about the removed features, and only to take their leavings away. They hold the exact text and names older versions used (the block markers, the skill marker line, the launchd label and the plist path), which is why those must not change; remove them when no Mac that ran 0.5 or earlier can still be upgraded.

## The command line

`jaffer` runs against the app's terminal and never starts one: with no app running, `status` and `doctor` say so and `daemon start` fails with *Jaffer is not running. Open Jaffer and run this again.*; `setup claude` fails that way only when the wrapper `~/.jaffer/bin/jaffer` (which the daemon writes at its start) is missing, `setup claude --status` and `--remove` always work, and `config get|set` fall back to reading and writing `config.json`. The commands are `hook <event>` (Claude Code's; above), `setup claude [--remove|--status]` (the hooks, nothing else; installing them needs the wrapper `~/.jaffer/bin/jaffer`), `status` / `doctor`, `config get|set <dot.path> <json>` (a value of the wrong kind is refused and the command says so), `daemon [status|stop]` (`stop` ends the terminal, and the app quits with it), `reset [--yes] [--delete]` and `--version`. Inside Jaffer's terminal `jaffer` is on the `PATH`; elsewhere *Install the `jaffer` command* from the palette links `~/.local/bin/jaffer`.

## Process boundaries and trust

The renderer is sandboxed (`contextIsolation`, no Node) and only reaches the daemon through the preload bridge; the main process checks the sender frame. Everything the watcher, the notifications or the window show from a hook payload or a command is redacted first (`src/shared/redact.ts`), and a sensitive command (`isSensitiveCommand`) is not named at all.

- **The window shows one page.** `shared/window-policy.ts` (`isAppUrl`) is used by `will-navigate` and by the IPC sender check: a file dropped on the window, or a link, never navigates it to a page that would then get the preload bridge (and with it a shell to type into). The `reveal` IPC opens Jaffer's own folder only; `openExternal` takes http(s) only.
- **What the page can ask of main** (each handler checks the sender with `trusted(e)`): the daemon's RPC, `open-external`, `reveal`, `app-info`, the update calls, `reset`, `set-login-item`, and since 1.0.0 `jaffer:save-text` (a save dialog, 32 MB, the person picks the place), `jaffer:open-path` (an editor link on the allow-list or Finder, for an existing absolute path), `jaffer:reveal-path` (Finder only) and `jaffer:focus-mode`, and since 1.3.0 `jaffer:trash-conversations` (`{ids}`: at most 200 UUID strings; main finds the files itself, asks the person, refuses a running conversation and moves to the Trash; only ids and reasons come back, never a path; see *Past conversations*); main pushes `jaffer:system-stats` to the page. **Nothing printed in the terminal is ever opened or run**: a path that a program printed can be shown in Finder or handed to an editor link, never `shell.openPath`.
- **A program may copy, not read.** The terminal answers OSC 52 *write* requests (so `ssh` can fill the clipboard) but never a *read* request (`osc52Provider`): whatever you last copied is not for the program that printed the query.
- **The redactor and the command-line helpers are on the hot path.** They run on the daemon's main thread over untrusted text (command output, forged marks), which also relays the terminal. Every redaction rule is bounded (no unbounded run of characters before a literal); `test/redact.test.ts` holds timing tests, because one unbounded rule once took 10 s on 9 KB. The helpers that read a command line (`isClaudeCommand`, `isInteractiveCommand`) slice their input to the `COMMAND_HEAD` (4096-character) head themselves, because the line comes from the shell's marks and can be forged at any length, and the window reads it too; timing tests feed them 1 MB and 8 MB crafted lines (unbounded patterns used to throw `RangeError` at about 8 MB). The readers added in 1.0.0 are bounded the same way (`findPaths`: the first 4096 characters of a line, word by word; `findPorts`: the first 64 KB; `isSensitivePath`: fails closed past 4096; `parseGitStatus`: the first megabyte) and have the same timing tests. **`redactText` throws a `RangeError` on a multi-megabyte single-run string**, so everything that redacts untrusted text clips it to `4 * COMMAND_HEAD` first: the daemon's `633;E` and `633;P;Cwd` payloads, `commandNotification` in main, and the window's `safeCommand`.
- **Files of the user's own** (`~/.claude/settings.json`, `~/.claude/CLAUDE.md`) are written through a symlink and keep their permissions (`writeFileAtomic(..., { preserve: true })`); only hooks tagged `jaffer-managed` and skills carrying Jaffer's marker line are ever removed; `reset` and the first start's clean-up refuse a folder that is a code checkout or holds none of Jaffer's own files.
- **What Jaffer keeps on disk**, in `~/.jaffer` (the folder is private, 0700, and the socket is 0600 in a 0700 folder): `config.json`, `window.json` (the window's place), `run/` (the socket and `jafferd.log`), `shell/` (the integration scripts), `bin/jaffer` (the wrapper that hooks and the CLI run), `updater.log` and, after a first start on an upgraded Mac, `migrate.log`. No screen, scrollback, command history, command output or transcript text is written. In `~/.claude/settings.json` only the `# jaffer-managed` hook entries (and, since 1.3.0, the one other change to Claude Code's folder: conversations the person picks go to the Trash, see *Past conversations*); `~/.local/bin/jaffer` only when asked.
- **What Jaffer keeps in memory** (and so loses with the app): in the daemon, the watcher's calls, counts, edited files and clocks, `live`, today's total and the time worked today (`workMs`), the pending permission requests (a view of at most 120 characters each), the last 15 turn lengths, which hook was seen when, and the git counts; in the window (1.4.0 adds the pane order, each terminal's info, the open close question, the context numbers, `usage5h`, the Today timeline, the one-time toast sets, the Setup data and MCP result, the tag/hidden/Storage/deep-search state, the Explain card, the tour and tip state), the command blocks, the recent commands (each with the folder it ran in), the pins, the turn history, the approval counts, the pending permission requests, the folder chip and cost-by-folder choices and a rename's draft, the commands that finished while it was away, the fail tracker and the side panel's last list of past conversations (`historyItems`, with titles); in main, the running command of each terminal (`runningCommands`), `digestAsked`, the focus-mode counts, the menu bar's last five commands and its list of past conversations (ids, folders, times and titles). The one number from this that reaches `config.json` is `claude.typicalTurnMs`. The 1.4.0 keys are settings, the person's own words or numbers (*Config*, below). The other 1.2.0 keys are settings or the person's own words, not collected data: `updates.seenVersion`, `history.names` (names the person typed), `history.pinned`, `claude.approvals`, `window.dropdown` and `appearance.seasonal`.

## Updates

`src/main/updates.ts` (`UpdateController`) drives `electron-updater` against the GitHub releases and decides nothing about the outside world itself: the updater, the dialog and ending the session are injected, so it is tested with fakes (`test/update-controller.test.ts`). `src/shared/update-policy.ts` holds the pure parts (prompt wording, when to ask, version checks, reading `codesign` output). The flow is check → download in the background → **ask** (native dialog: *Updating restarts Jaffer and ends your terminal session: the shell and anything running in it stop, and a fresh terminal starts.*; Claude working is said too; the default button is *Later* and Esc means Later) → on yes, `prepareInstall` stops the app's own child (the shell ends) and the app calls `quitAndInstall`; a watchdog (60 s) or an updater error brings the app back with a fresh terminal and an error dialog. `autoInstallOnAppQuit` is off on purpose: quitting must never replace the app behind a running session. Only a packaged, Developer ID signed app checks (the bundle's signature is read at startup), only non-prerelease releases count, and errors are logged to `~/.jaffer/updater.log` and shown in Settings, never as a dialog unless the user asked. The release side is `scripts/release-mac.sh`: it checks `latest-mac.yml` and uploads it after everything it names.

## The window

The renderer is a terminal card on a canvas, with a thin title bar above (folder, branch and git counts, what is running, chips for what Claude is doing, and the cost). Since 1.1.0 a **side panel** sits at its right (*The side panel*, below). There is no left sidebar, drawer or status bar; the additions of 1.0.0 are the ones named in *Command blocks* and *The title bar and what feeds it*, below, and the calm-window UI test lists what may sit in the workspace, the stage and the terminal area (and that there is exactly one panel). Since 1.4.0 the terminal area holds `.panes`, whose only children are the `.pane`s of the split view (*Terminals*, above); there are no title-bar buttons for it. Colours come from layered tokens derived from the active theme (`themes.ts`): `--chrome` is the canvas, `--surface` the card on it, `--raised` things on that. A theme change repaints the whole app. Settings has seven sections: Appearance (which ends with a *Window* group: what closing does and the menu bar item), Terminal, Claude Code, Privacy and permissions (1.4.0), Help (1.4.0), Updates and Reset; the first run asks about Claude Code and then shows the privacy switches (the last stage, `PrivacySwitches`, also on the plain-terminal path), and offers the tour once.

- The title bar reads `session.info` (folder, branch) and keeps itself live from `pty.start`, `pty.command` and `pty.cwd` events. The ring beside the folder is `processBadge` (`src/shared/process-badge.ts`): an ordinary command spins while it runs; Claude Code spins only while its hooks say it is working. The cost figure (`CostChip`) is on the right while `claude.showCost` is on (more below).
- The companion (`Pet.tsx`, `src/shared/pet-mood.ts`) is an SVG in a corner of the terminal card, chosen in Settings → Appearance (`appearance.companion`, listed in `src/shared/companions.ts`; anything unknown is the mole; since 1.3.0 `appearance.petSize`, `small`, `normal`, `large` or `huge`, factors 0.75, 1, 1.5 and 2.25 by `petScale`, an unknown value counts as `normal`: `Pet.tsx` sets `--pet-scale` on the corner, which the stylesheet applies as `scale` anchored at the bottom right, so the layout never moves; a factor above 1 is capped to half the terminal area's width and height (measured on the corner's unscaled size, re-measured when the area or the corner resizes) and never below 1, so on a small window *huge* shows smaller than 2.25). The mole is the original; the other five are scenes (below). Every pose is a `[data-mood]` state (sleep, rest, dig, alert, cheer), so it is right with Animations off too; the motion is added only under `:root:not([data-motion='off'])` and stops under macOS Reduce motion. It ignores pointer events. It also shows the tool Claude is running: `data-tool` is the category of the session's tool (`petTool`, only while working), and the mole shows a prop for it (a book for reads, a hammer for writes, an antenna for web, the hard hat for agents; shell is the plain digging) while the scenes change hue or rhythm for reads and writes, and are denser for agents. After ten quiet minutes (no Claude work, no command, `isDozing`) it dozes (`data-idle="doze"`: dimmer, slower, Zzz; any activity wakes it); a command that failed three or more times in a row (same text, `FailTracker`, memory only, never a sensitive command) and then exits 0 plays a short burst of sparks ("fixed it"); a bell flinches it (2 s debounce) and, while the window is not in front, bounces the Dock icon once (`maybeBounce` in main: informational, at most one in 5 s, dropped in focus mode). The props are poses, so they show with Animations off too; the motion, the burst, the flinch and the doze breathing stop with Animations off and under macOS Reduce motion. A helper mole stands for each running subagent (`ClaudeSession.subagents`, at most three, `src/shared/pet-crew.ts`; its own `data-tool` from `subagents[].tool`); a helper whose agent finished cheers for a moment and leaves. Effort grows with time (`src/shared/pet-effort.ts`: 30 s, 2 min, 5 min since the turn or the command started, or since the helper's own `SubagentStart`; `ClaudeSubagent.startedAt`, `info.busySince`): `data-effort` 0–3 sets the digging tempo (`--t`) and adds the sweat drop, the hard hat and a bigger pile, all static under Animations off. Background agents outlive the turn that started them, so `Stop` does not end them: `SubagentStop`, the session ending, or half an hour of silence does.
- The scenes (`Scenes.tsx`, geometry in `src/shared/scene-geometry.ts`): **Matrix** (digital rain, an agent is a brighter coloured column), **Agent network** (a hub and up to three nodes passing packets), **Warp** (a starfield at speed, a wingman ship per agent), **Radar** (a sweep and a blip per agent) and **Reactor core** (counter-rotating rings, equaliser bars, satellites). They take the same inputs as the mole (`petMood`, effort, the crew from `pet-crew.ts`), draw into one 240×80 SVG frame, and follow the same rules: the still pose of every mood is the base style, motion is added only under `:root:not([data-motion='off'])` and ends at once under macOS Reduce motion, colours are theme tokens only (`--ok`, `--info`, `--violet`, `--accent`, `--warn`), and the corner ignores pointer events. Everything that varies (rain columns, star positions, node places) is a pure function in `scene-geometry.ts` with no randomness, so a render is the same every time and `test/scene-geometry.test.ts` can pin it. Settings shows each one live in a radio group (`CompanionPreview`); the effort tempo is the `--t` variable, as for the mole.
- **Seasons** (1.2.0, `appearance.seasonal`, on by default): `seasonOf(date)` (`src/shared/season.ts`, pure) gives `halloween` (Oct 24 to Nov 1), `winter` (Dec 15 to Jan 3), `valentine` (Feb 12 to 15) or `none`; `currentSeason()` (`src/renderer/season.ts`) is `none` with the setting off, reads the date, and takes a `?season=` override only when the page has `debug` in its query (a test hook). The main mole gets `data-season` and a `.pet-season` group (a pumpkin, a Santa hat, a heart; hidden while its hard hat shows), a scene's frame gets `data-season` and nine small `.sc-flake` dots whose drift is a CSS animation added only under `:root:not([data-motion='off'])`. The look uses theme tokens, except the winter colour (a fixed off-white for the brim and the snow, so it shows in light themes too). Read at render time: no timer at midnight.

## The side panel

Since 1.1.0 the window has one column at the right of the terminal card (`components/SidePanel.tsx`, in `.workspace` beside `.terminal-area`). It is open by default; `⌘B`, the button at the far right of the title bar, *Toggle side panel* in the palette, *View → Toggle Side Panel* and *Settings → Appearance → Show the side panel* toggle it. It has exactly three sections, **Now**, **Past conversations** and (1.4.0) **Setup**, plus temporary children above them, the **What's New** card (below) and (1.4.0) the **Explain** card, and shows nothing the window does not already have except what the privacy switches allow (below): it reads the same `claude.state` push as the title bar and the same `claude.history` RPC as the menu bar, and everything it shows about a command or a file goes through the same redaction as before. It has no input of its own that reaches Claude, and the only thing it ever types into the shell is the resume line of a past conversation, after the person's click or Enter (*Past conversations*, below). The UI test pins its children: the handle, the cards when there are any, Now, the conversations and Setup.

- **Config.** `panel: { open: boolean, width: number }` in `config.json` (default open, 300). `panelWidth` (`src/renderer/panel.ts`) clamps what is shown to whole pixels from 220 to 480 (300 for anything that is not a number); the file may hold any number and `jaffer config set panel.width 400` works. The window writes a change at once into its own copy (`patchPanel`), then patches the file, so pressing `⌘B` twice ends open and a drag does not jump back.
- **`⌘B` has two doors.** The View menu's accelerator (`toggle-panel` in `src/shared/menu-spec.ts`, so the menu, the palette and a test agree on one id) and the page's own key handler (which the dev bridge needs, and which also catches the key when the page has focus). `togglePanel(via)` ignores a press that arrives from the other source within 250 ms, so one press is one toggle whichever arrives first, or both.
- **Layout and fit.** Opening or closing changes the panel's layout width at once, so the terminal fits **once** (`pty.resize` is called one time, not once per frame of an animation: each SIGWINCH makes Claude Code's TUI redraw, and many in a row duplicate its output). The slide is transform and opacity over 180 ms (`data-anim` `in` or `out`; closing keeps the panel mounted for those 180 ms, then it unmounts); there is no slide at first mount, with *Animations* off or under macOS Reduce motion. The panel's left edge is a handle (`.sp-handle`, `role="separator"`, `←` / `→` change the width by 20 px): while it is dragged the panel follows the pointer, `layoutHold` is true and `TerminalView`'s `refit` does nothing, and on release the width is written and the hold drops, so the terminal fits once (`requestAnimationFrame(refit)` from a signals effect). A window resize fits as before.
- **Closed, nothing runs.** A closed panel renders nothing: no timers, no reads. Closing and opening it again mounts it fresh, which is also what refreshes the list.
- **Now** (`NowCard`, the pure model is `nowCardModel` in `panel.ts`). One card with the state (*Claude is not running*, idle, working, or needs you), the tool and the turn's time while it works, a progress bar against a typical turn (the title-bar ring's `progressFraction`), the cost (`costFigure`, the same figure and the same *estimate* wording as the title bar's chip, only with `claude.showCost`, and *so far* while it grows), today's total against the daily budget (the budget's colours at 80 % and over), a line for each running agent (numbered, with its tool and time, never an id), this turn's counts (`3 reads · 2 edits · 1 shell`; a stale turn's are dropped, as in the title bar) and up to eight edited files by name (`+N more`; a click shows the file in Finder, `jaffer:reveal-path`). Since 1.4.0 the card also has a **context meter** (`context` in `nowCardModel`: `Context 62% of 1M` with `role=meter`, `warn` from 80 %, `danger` from 92 %, tokens only with no fraction when the model has no window or the tokens pass it), the **last-5-hours** line (`usage5h`), a collapsible **Today** list (`todayTimeline`: the last 20 turns that ended today, newest first: time, length, tool counts, files, cost; entries of `turnHistory` now also hold `at`, `counts` and `files`), and the daily work-time budget's level on the worked line (`workedLevel`). The context and the 5-hour line exist only with `claude.showCost`. When a turn ends the counts give way to the summary line (`Claude finished in 1m 12s · 1 read · ≈ $0.04`, the toast's text). A needs-you card names the tool and says to answer in the terminal; what Claude asks stays in the title bar. It ticks once a second only while Claude works, and with the slow clock otherwise. Since 1.2.0 it also has (a) **turn bars**: `turnBars` (`claude-ui.ts`, pure) turns the last 20 entries of `turnHistory` (length, cost) into an SVG of 6 px bars, 28 px high, the height by length against the longest and a tint (`data-level`) by cost against the costliest in view (equal costs all low; no cost text with `claude.showCost` off), a `<title>` on each (`1m 12s · ≈ $0.04`) and an `aria-label`; shown from two turns on; (b) **the worked-today line** (`worked` in `nowCardModel`): the daemon's `today.workMs` plus the running turn, hidden under a second, independent of the cost switch; and (c) while permission requests wait, `ApprovalAsk` in place of the hint (*Permission prompts from the notification*, below).
- **Past conversations** (`components/Conversations.tsx`; the pure parts `groupByDay`, `filterByFolder`, `conversationRow` in `src/shared/history-label.ts`). The list is the daemon's `claude.history` answer (see *Past conversations*, below), grouped under *Today*, *Yesterday* and `Mon 12 Oct` (local midnight; day names are fixed words, not the locale's; another year adds the year), each row (`.conv-item`, holding the `.conv-row` button and a separate `.conv-copy` button) the title in bold on one line (*Conversation* when there is none: the 30 newest have one), then the `~/…` folder and `time · how long · cost` (a dash when there is none; no cost when *Show what each answer cost* is off). A search box filters by name, title and folder (and, with `permissions.deepSearch` and its *Search text* switch, by the text of the conversations: below); below it, **folder chips** (*All* and the five most used folders, `topFolders`; shown when there are two folders or more; component state only) and a **Cost by folder** toggle (only with `claude.showCost`: `costByFolder(items, now, home)`, today and the last 7 days for the five busiest folders, from the costed conversations already in the list, which are the 30 newest, and it says so). Each row has, on hover or focus, a pencil (rename, also F2: an inline input prefilled with the person's own name only, Enter saves to `history.names`, Esc cancels, an empty name removes it; a blur cancels) a star (pin: `history.pinned`, a *Pinned* group above the days) and a trash button (*Move to Trash*, 1.3.0), and (1.4.0) a tag button and a hide button. The header has a *Remove…* button with a small menu (*This folder (N)*, only while a folder chip is active, *All listed (N)* and, since 1.4.0, *Older than 30 / 60 / 90 days…*; the same `Menu` as the gutter mark's), and `Delete` or `Backspace` on the focused row (not in an input) asks to remove that one: each calls `window.jaffer.trashConversations(ids)`, which asks the person natively (see *Past conversations*); on the answer the moved ids leave `history.pinned`, `history.names` and the list, the list is read again and a toast says how many moved and why any did not. The toggles row has *Cost by folder*, *Storage* and (while a listed conversation is hidden) *Hidden (N)*; tag chips filter by one tag at a time (memory). Rows are keyed by conversation id so keyboard focus survives a refresh or a pin. A click or Enter **resumes** the conversation: `resumeAction(info, conversation)` (`src/shared/resume-action.ts`, pure, unit-tested) returns `type` (the renderer writes it to the terminal, shows *Resuming…* and gives the terminal the focus), `copy` (the clipboard and a toast with the reason) or `none` (a bad id: an error toast); the small copy button copies `resumeLine` and types nothing; ↑ and ↓ move the selection, Esc returns to the terminal. `⇧⌘O` (and the menu bar's *All Past Conversations…*) open the panel when it is closed and focus the search (`showConversations`, `panelFocusSearch`; a later `⌘B` does not take the keyboard).
- **When the list is read.** When the panel opens (it mounts), after a turn that went from working to idle, and on the refresh button; the panel itself never reads while it is closed. Since 1.2.0 the command palette also reads it every time it opens and ⇧⌘R reads it every time it runs (`readHistory` in `src/renderer/resume.ts`, always with `include`: the pinned ids), with the panel closed too. Only the newest answer counts (a sequence number), and one that arrives after the panel closed is dropped. The last answer is kept in memory (`historyItems`) so a panel that opens again shows it at once, and an error is a toast plus a quiet note in the section.
- **What's New** (`components/WhatsNew.tsx`, `src/shared/whats-new.ts`, `src/shared/mini-md.ts`, `scripts/gen-release-notes.mjs`). `RELEASE_NOTES` (`src/generated/release-notes.ts`, newest first, `{ version, md }`) is generated at build time from every `docs/releases/v*.md`: the leading `#`/`##` title and the standard last line (*Updating from 0.2.x…*) are cut, and `--check` is a test. `unseenNotes(notes, seen, current)` gives the notes newer than `seen` and not newer than the running version, five at most. The *seen* version is `updates.seenVersion`, else (never dismissed) `1.1.1` for an `onboarded` Mac (the last version without notes) and the running version for a first start (`effectiveSeen`). The card (title *What's new in <newest>*, the notes, **Dismiss**, **All versions**) renders the notes with `parseMd`, which returns data (headings, paragraphs, bullets; bold, italic, code), never HTML: the input is clipped (200 KB, 4096 per line) and the scan is linear, with timing tests on 1 MB and 8 MB. Dismiss writes `updates.seenVersion = <running version>`; the first onboarding does too. After an update a toast *Jaffer updated to <version>* (not when the panel is open, which already shows the card) has a *What's new* button that opens the panel; the Help menu's *What's New…*, the palette's *What's new* and the menu bar item's *What's New in <version>* line (present only while notes are unseen: main mirrors `onboarded` and `updates.seenVersion`) open it any time, and with nothing unseen it shows the history (a *Close* button, every version collapsible, the newest open). It adds no data and no RPC.
- **Dropped on purpose:** a chat or prompt box, tabs or more sections, a left panel, a second window, typing anything but the resume line of a past conversation, and a panel at less than 220 px.

## The menu bar item and closing the window

Since 1.0.1 Jaffer has one thing outside its window: an icon in the menu bar (`window.menuBar`, on by default). Everything is in the main process (`src/main/main.ts`), on top of pure pieces in `src/shared` that are unit-tested; the Electron wiring itself (the `Tray`, the dialogs, the Dock) is not exercised by a test (see the README's *Not verified here*).

- **The icon** shows the state of the terminal's Claude, from the `claude.state` push main already reads (`trayState` in `shared/tray-state.ts`: a session that needs you wins, then one that works, else idle). The glyphs are the mole's head: eyes closed for idle, two digging frames for working, a dot for needs-you. They are template PNGs at 18 and 36 px (macOS tints them for a light or dark menu bar), generated by `scripts/gen-tray-icons.mjs` into `src/generated/tray-icons.ts` (`npm run gen:tray`; `test/tray-icons.test.ts` runs the generator with `--check` and decodes every PNG; the PNGs use stored deflate blocks so the output is the same on every machine). `TrayIconPlayer` plays them with one timer at most: working alternates two frames every 500 ms, a new needs-you flashes the alert icon three times (400 ms) and then stays on it, idle and alert stand still.
- **The text** beside the icon (`window.menuBarTitle`, `trayTitle`): nothing (the default), this session's cost, the running turn's time (`45s`, `4m`, `1h 2m`; a 1 s timer runs only while that mode is on and a turn runs) or today's cost. The costs follow `claude.showCost`, say `≈`, and are estimates like the title bar's.
- **A click** on the icon shows the window, or hides it while it is in front (`toggleWindow`, the same function as the global hotkey). **A right click** opens a menu built fresh each time: status lines (*Idle*, *Working · Bash · 1m 12s*, or *Needs you: Bash* and Claude Code's own wording, all redacted, one line, at most 60 characters; a click shows the window), Show or Hide Jaffer, *Recent Commands* (the last five, from `RecentCommands`: a click **copies** the command, nothing is typed), *Past Conversations* (the five newest: `<title, at most 40 characters, else the folder's name> · <how long ago>`; a click copies `claude --resume <id>`: the menu is main's, which cannot type), Focus Mode, Settings… and Quit Jaffer; since 1.2.0 a *What's New in <version>* line near the top while release notes are unseen (a click shows the window and opens the card). With ⌥ held when the menu opens it adds lines: the cost so far (only with `claude.showCost`), this turn's tool calls (`3 reads, 2 edits`) and the repository's counts (`git +2 ~3 ↑1`, a `session.info` call capped at 1 s). That is where the "peek panel" of the plan went: there is no second window.
- **Closing** (`closeDecision`, `shared/close-action.ts`): the ✕ and `⌘W` (the menu's *Hide Window* calls `window.close()`, so both arrive at the window's `close` event, which is prevented and handed to `closeWindow`) follow `window.closeAction`:

  | `closeAction` | menu bar item | window in full screen | result |
  |---|---|---|---|
  | `quit` | any | any | `quit`: `quitFromMenu`, so it asks when Claude or a command runs |
  | `ask` | there | any | `ask`: a sheet, *Hide to Menu Bar* / *Quit Jaffer* / *Cancel* (the default and Esc: Cancel) |
  | `ask` | none | no / yes | `hide` / `leave-full-screen-then-hide` (the sheet's words would be false) |
  | `menubar` or anything else | any | no / yes | `hide` / `leave-full-screen-then-hide` |

  Whether something runs never changes the decision: the quit question asks about running work itself. **Full screen:** hiding a window that is in full screen leaves an empty Space with nothing to click, so `hideWindow` first calls `setFullScreen(false)` and hides on the `leave-full-screen` event, or after 2 s if it never comes; showing the window calls a pending hide off. The hotkey and the icon's click use the same function. **The first hide** while the icon is there shows one notification (*Jaffer is still running in the menu bar*) and sets `window.hintShown`. A hidden window keeps the terminal, Claude Code and the hooks running; the icon, the hotkey, a notification's Show button and (unless hidden) the Dock icon bring it back.
- **The Dock icon** (`window.menuBarOnly`, `syncDock`): `app.dock.hide()` only while the icon exists and the setting is on, `show()` otherwise, acting on a change only. `showWindow` does not show the Dock icon while it is hidden on purpose. Settings disables the switch while the icon is off. If the icon cannot be made (the image fails to load), it is simply not there: no crash, and the Dock stays.
- **Drop-down mode** (1.2.0, `window.dropdown`, off by default, needs the hotkey: Settings disables the switch while the hotkey is empty). `syncHotkey` registers `hotkeyToggle`: with the setting off, or with the window in full screen, it is the plain `toggleWindow`; with it on, a visible and focused window hides, and otherwise the window (made first when it does not exist) is placed by `dropdownBounds(workArea of the display under the pointer)` (`src/shared/window-policy.ts`: the work area's x, y and width, and a height of 45 % of it, at least `MIN_WINDOW_HEIGHT` = 420, the window's `minHeight`, and never more than the area) and shown, without animation. While it is on, the window hides when it loses focus (`blur`), provided a hotkey is registered, it is not in full screen and **no dialog of Jaffer's own is open**: `dialog` in `main.ts` is a wrapper whose `showMessageBox` and `showSaveDialog` count open dialogs (`dialogsOpen`), because a native sheet takes the focus from the window; every dialog of ours must use the wrapper. The place a drop-down window takes is never written to `window.json` (the bounds writer does nothing while the mode is on, and a pending debounced write is dropped), so switching it off puts back the saved bounds (`restoreBounds`: the default 1280 by 820 centred when nothing was saved; after leaving full screen when it was in it). The tray click, the Dock icon and a notification's Show still show the window where it is. No second window and no Dock change.
- **Quitting** from the icon's menu is the app menu's custom item (`quitFromMenu`); every quit rule in *The app owns the session* holds. The icon is destroyed before the app exits.

## Past conversations

The side panel's list (*The side panel*, above; ⇧⌘O, *Past Claude conversations…* in the palette and the Shell menu focus its search) and the menu bar's list (the five newest, right in the menu, with *All Past Conversations…* below them) read the same thing: the daemon's `claude.history` RPC (`{ items }`, at most 50, newest first) from `src/core/claude/history.ts`. It reads Claude Code's own transcripts, which Jaffer otherwise reads only for token counts (read-only, apart from *Removing*, below), and takes from them **only** the session id (the file name), the folder (`cwd`), the first and last timestamps, for the newest 30 and only with `claude.showCost` the cost and, for the newest 30 (1.1.1), a **title**. Each item is exactly `{ id, cwd?, title?, startedAt?, endedAt, durMs?, usd? }` (nothing is added for a pinned conversation or for a name: names are the person's, in the config); no other prompt, reply or tool input is kept, and `test/claude-history.test.ts` plants secret words and checks that none comes out.

- **`include` (1.2.0).** `claude.history` takes `{ include?: string[] }`: the pinned ids (`pinnedIds` of `history.pinned`). Only the first 50 entries are looked at and each passes `isSessionId`; such conversations are listed after the newest `limit` even when older, with a title, and with a cost only when they are among the 30 newest. Anything else in the parameter is ignored.
- **Removing (1.3.0): the one write.** `jaffer:trash-conversations` (main) hands the ids to `trashConversations` (`src/main/trash-conversations.ts`, no Electron import; main passes `{claudeDir, trashItem: shell.trashItem, confirm, liveIds}`). Ids are validated (`isSessionId`, at most 200 = `MAX_REMOVE`, each once); `liveIds` asks the daemon's `claude.state` and takes every session that is not ended: those are refused (*running*), and if it cannot be asked nothing is moved and nothing is asked (*unknown*: never a guess). The files come from `conversationFiles(claudeDir, ids)` in `history.ts` (read-only: names only, by the confinement below, `lstat` for every step, the real path inside the root; a link is neither followed nor listed): `<folder>/<id>.jsonl` and, when it is a real folder, its sibling `<id>/` (subagent transcripts and tool results); an id with no file is *not found*. The person is asked once, with the number of conversations found (a native dialog through main's counting wrapper, *Move to Trash* / *Cancel*, Cancel the default; the window is the sheet's parent only while it is visible), so that number can be lower than the menu's (the running and the missing are dropped). After the answer the live sessions and the files are looked at again (a conversation resumed, removed or swapped for a link meanwhile is refused), then each file and its folder go to the Trash with `shell.trashItem`; one that fails is *error* and the others go on. Nothing is deleted outright, and the Trash can put them back. The guard sees only the sessions Jaffer's own hooks report: a `claude` in another terminal app is not seen, and a path-based `trashItem` leaves a small window between the second look and the move (a parent folder swapped for a link in those milliseconds).
- **Where:** `<claudeDir>/projects/<folder>/<session id>.jsonl`, with `claudeDir` = `$CLAUDE_CONFIG_DIR`, else `~/.claude`.
- **Confinement:** the root is `realpath(<claudeDir>/projects)`. Only real folders (`lstat`) and regular files whose name is `<uuid>.jsonl` (`isSessionId`) count; a symlink, a subfolder (`<uuid>/subagents/…`), another extension and a loose file are skipped. A file is checked again before it is read (its realpath must lie under the root) and opened `O_RDONLY | O_NOFOLLOW`. A missing folder gives an empty list.
- **Bounds:** every read is async (the daemon's thread is also the terminal's relay) and one file at a time. The first and the last 64 KB of a file give the `cwd` and the timestamps (only whole lines, and only a line's own top-level `cwd` and `timestamp`; the `cwd` must be an absolute path of at most 4096 characters without control characters). The cost needs the whole file, so it is read only for the newest 30 and only up to 24 MB (`MAX_READ`, shared with the cost reader), and no price (an unknown model) or no response gives no `usd`. **The title** is the one text taken, from the same two 64 KB pieces and nothing else: the latest `customTitle`, else the latest `aiTitle`, else the latest `summary` line, else the first line of the first real user message (`type: 'user'`, role `user`, not `isMeta`, `isSidechain` or `isCompactSummary`, not starting with `<`, so `<command-name>` and `<local-command-caveat>` lines are skipped). It is clipped to 4096 characters before `redactText` (a token is masked whole before the cut), stripped of control and format characters, and cut to 80. A cache by path, size and mtime (at most 500 entries) means a file that did not change is not read again. It lives in memory and is never written.
- **Use (1.1.1): a click resumes.** The panel's list filters by title and folder. A click or Enter on a row types, **only at an idle prompt** (`info.busy` empty: the shell's marks say nothing runs), Ctrl-E, Ctrl-U, Ctrl-X Ctrl-K (clears a half-typed line wherever the cursor is; bash's Ctrl-U kills only before the cursor, and Ctrl-X Ctrl-K is zsh's kill-buffer for a buffer of several lines, a bell in bash), then `claude --resume <id>`, or `cd '<folder>' && claude --resume <id>` when the shell is in another folder (`shellQuote`: `'` written `'\''`), then Enter. `resumeAction` decides: a bad id (`isSessionId` through `resumeCommand`) does nothing; while Claude runs (`isClaudeCommand`) or any other command runs it only **copies** and says why; a folder that is not absolute, is over 4096 characters or holds a control character or a backslash is treated as unknown (only `claude --resume <id>` is copied); everything else is typed. A typed line locks further typed lines until the next `pty.start` or 2 s, so a double click types once (the second click says "Already resuming…"). Since 1.2.0 the logic is in `src/renderer/resume.ts` (`resumeConversation`, with that lock), which the panel's rows, the palette (Enter on a conversation: two typed characters or more, at most five, matching name, title or folder; the list is read at each open) and **⇧⌘R** (`resumeLast`) share; `resumeLast` always asks `claude.history` first, because a list the window kept may be hours old (a failed read falls back to the list it has, a missing list gives a toast), then takes `lastConversation(items, info.cwd)`: the newest conversation whose folder is the shell's, else the newest. A name given with the pencil (`history.names`, parsed by `src/shared/history-names.ts`: `"<session id> <name>"`, the id by `isSessionId`, names cleaned of control and format characters and cut to 80, at most 200 entries, bad entries skipped) replaces the title in the rows, the search, the palette and the menu bar's labels (main reads the names from its config mirror). `isClaudeCommand` (`shared/process-badge.ts`) also recognises a line that starts with exactly the `cd '<folder>' && ` this types (`RESUME_CD`: quotes written `'\''`, no backslash; the cd read within `5 * COMMAND_HEAD`, the rest by its usual head), so a resumed Claude counts as Claude for the badge, ⇧⌘C, the toast and the daemon's `endAll`. The copy button on the row copies the same command and types nothing. Known gaps (README, *Not verified here*): forged OSC 133/633 marks can fake an idle prompt, and a PS2 continuation prompt and the shell's vi command mode count as idle. The menu bar's items still only copy `claude --resume <id>`. The menu bar keeps the last answer in memory and refreshes it each time the menu opens (the menu waits up to 400 ms for it, so the first, cold call can delay the menu by that much) and after each finished turn.

## Command blocks

The shell's marks (OSC 133 `A` prompt, `C` output start, `D;<exit>` end, and 633 `E` for the command line) are read a second time **in the window**, on the terminal's own xterm parser (`src/renderer/blocks.ts` is the pure model, `components/Blocks.tsx` the view). The handlers only observe (they return false, so nothing else about the terminal changes) and exist only while `terminal.blocks` is on. A block is one command: its prompt line, where its output starts and ends (xterm markers), its command text, its exit code (a safe integer, else unknown) and its start and end time. At most 500 are kept.

- **Where they come from, and when they are gone.** Only from output the window has received since it attached: a snapshot carries no marks, so after a re-attach, a daemon `pty.reset` (a restarted shell), `ESC c` or *Clear screen* (⌘K) the blocks start again (`blocks.reset()` runs before every `term.reset()`; the model also drops a block whose prompt marker xterm discards, scrollback trimmed or cleared). The prompt that is waiting after a clear keeps its block, unanchored, until its output starts. Marks that arrive in the alternate screen are ignored (xterm hides decorations there too). The command text of a block is a `633;E` payload cut to `4 * COMMAND_HEAD` before it is unescaped and shown only through `safeCommand`; the model never keeps command history anywhere but its list of blocks, in memory.
- **What the window shows.** A 1-cell mark in a small left gutter of the terminal (`.gutter-mark`, `data-state` ok, fail or run; the tooltip has the start time and how long it took, never the command); hovering it tints the block's output (`--accent-soft`), a click selects the output, ⌘↑ / ⌘↓ jump to the previous or next prompt. When the view is scrolled up into a block's output a **sticky header** at the top of the card shows its command (cut to 80 characters) and exit mark; a click scrolls to the prompt (pinned lines push it down: `--pins-h`).
- **The right-click menu** on a mark (`.ctx-menu`): *Copy command* (the raw text, to the person's own clipboard, not offered for a command `isSensitiveCommand` flags), *Copy output*, *Save output…* and *Copy as image* (1.2.0: only when the output is still on the screen; `block-image.ts` lays out the `$ <command>` line, through `shownCommand` so a sensitive command has none, and the output cut to 200 lines of 160 columns with a final `…`, ANSI sequences and control characters removed, tabs to stops of 8, and draws it on a canvas in the terminal's font and theme colours at 2x, or 1x for a very large one, never above 16384 px or about 40 megapixels; `navigator.clipboard.write` with a `ClipboardItem` of `image/png`; a toast says *Copied as image*, a failed draw or write says so, and nothing is saved) and *Copy as Markdown* (⌥⌘C does the same for the selection: a fenced block, and the first line `$ <command>` through `safeCommand` when the selection is inside one block). The output text (`blockOutputText`) joins wrapped lines, drops trailing empty lines and stops at 32 MB with a note. If the output was erased from the screen (Ctrl-L), only *Copy command* is offered and the others say nothing is left. *Save output…* is the IPC `jaffer:save-text`: main checks the sender, takes a string of at most 32 MB (bytes), opens a save dialog in Downloads with a name that `safeFileName` made (the first word of the command, `NAME=value` prefixes skipped, `output.txt` for a sensitive one) and writes where the person chose; Jaffer keeps nothing.
- **Long commands.** While the window is not focused, a command of 30 s or more that ends is remembered (up to 50, memory only); when the window comes back one toast says `make finished in 4m 12s (exit 0)` (the newest command through `safeCommand`, and "and N more").
- **Dropped on purpose:** collapsing output (xterm has no folding).

## The title bar and what feeds it

Everything here is derived from the hook state (above) and the shell's marks; nothing is typed, and nothing is answered except by the opt-in permission prompts (above), after a click.

- **The ring** (`.running`, the existing spinner) spins while a command runs; for Claude Code it spins only while its hooks say it works. With `claude.typicalTurnMs` known it fills (a conic gradient, `--p`) against the typical turn length (`progressFraction`), stays full and pulses past it, and turns dotted while the session is `compacting` (a toast says so once). Its tooltip is the session clock (`Claude · 42 min · 9 turns · ≈ $1.20`; the cost only with `showCost`) and a line per running agent with its elapsed time.
- **The tool strip** (`ToolStrip.tsx`, switch `claude.toolStrip`) is a 2 px line under the title bar with one segment per call of the current turn (`turnCalls`: only calls that began at or after `turnStartedAt`), coloured by category (the danger colour for a failed call), as wide as it took (a call still running grows with a 1 s clock that runs only while Claude works), 8 px tall to hover (tool name and duration). The newest segments stay in view. It empties at the next prompt.
- **Chips in the pill:** the git counts after the branch (`+2 ~3 ?1 ↑1 ↓0`, zeros left out); the **editing chip** while `Edit`, `Write`, `MultiEdit` or `NotebookEdit` runs (the file's base name; a click reveals it in Finder through `jaffer:reveal-path`); the **needs-you chip** while the session waits (the tool, the redacted notice cut to 60 characters, and "2nd time" when this session already answered a prompt for that tool; the counts are in memory); the **port chip** (below). They are read-only, except that with the opt-in permission prompts the needs-you chip offers Deny and *Answer in terminal* (never Allow) while a request waits: Jaffer otherwise never answers Claude Code's prompt.
- **Git status.** On each `prompt` event of any pane (debounced 300 ms, one timer and one result per pane) the daemon runs `git status --porcelain=v2 --branch` in the project's repository root (`resolveProject`) and adds `git: {staged, changed, untracked, ahead, behind}` to that pane's `session.info`; nothing is broadcast, the window asks for `session.info` again 1.5 s after each prompt. How it is made safe (argv array, 1 s, 1 MB, no optional locks, `core.fsmonitor` off, submodules ignored, skipped for a repository whose own config names a filter driver, skipped on a Mac without the developer tools) is in CLAUDE.md; a failure or a repository without git is simply no counts.
- **The cost chip** shows what the last answer cost, or, while Claude works and `claude.liveCost` is on, a greyed *≈ $0.03 so far* (the daemon's `live`); it turns `warn` at 80 % and `danger` at 100 % of `claude.dailyBudgetUsd` (today's estimate). Hovering shows (a plain CSS hover card, no native tooltip) this answer, the session, today, the estimate wording, and two small SVG sparklines of the last 20 turns (length and cost) drawn from `turnHistory`, which the window keeps in memory. An unknown model price plots as 0.
- **The turn summary** (`claude.turnSummary`): when the current session goes from working to idle without being cut short and the turn took 10 s or more, a toast says `Claude finished in 1m 12s · 3 reads, 2 edits, 1 shell · ≈ $0.04` and lists up to five edited files (base names) as buttons that reveal them in Finder, with "+N more". It waits for the answer's cost (up to 3 s) before it shows.
- **The glow** (`StageGlow`, `appearance.glow`) writes `data-glow` on `.stage` (needs-you pulse, steady while working, one flash when a turn ends) from its own signal effect, so a state push does not re-render the whole window. Not with Animations off or Reduce motion.
- **The folder** slides out and in when it changes (200 ms; not with Animations off).
- **System stats** (`appearance.systemStats`, off by default). While it is on, main samples CPU (all cores, `os.cpus()` deltas) and memory in use every 5 s and sends `jaffer:system-stats` to the window (nothing is sampled, and no timer runs, while it is off); the window draws three small bars, with the battery from `navigator.getBattery()` and hidden on a Mac that has none.
- **The title bar is a drag region**, so every part that shows a tooltip or takes a click (the folder, the ring, the chips, the cost, the strip's hit row) is `no-drag`, or macOS would swallow the hover; the pill itself, its dot and the empty bar stay draggable. That is checked here through computed style in Chromium only.

## Terminal conveniences

- **Paste guard** (`terminal.pasteGuard`): a capture-phase `paste` listener on the terminal host stops a paste of two or more lines (`\r\n`, `\n` and a lone `\r` each end a line; a trailing break does not count) before xterm sees it and shows a bar: *Paste N lines?*, the first line (redacted, 80 characters), **Paste** (Enter) or **Cancel** (Esc). Dropping a file is not a paste and is unchanged.
- **Links** (`findPaths`): a link provider reads one buffer line at a time and finds `path`, `path:line` and `path:line:col` (absolute, `~/`, `./`, `../`, or `dir/file.ext`; a bare `name.ext` only with a line or a known extension; never inside a URL; at most 20 per line). ⌘-click calls `jaffer:open-path`: main checks that the path is absolute, at most 4096 characters and exists, then either hands the template from *Open file links in* (an allow-listed editor scheme only, path encoded per segment) to the browser's opener, or reveals the file in Finder. A relative path is resolved against the session's folder, not the block's, and a path that wraps over two lines is not found. A printed path is never opened or run.
- **Ports** (`findPorts`, `terminal.portLinks`): while a command that is not Claude Code runs in the normal screen, each `pty.data` chunk is scanned (the first 64 KB, ANSI stripped, bounded) for `localhost`, `127.0.0.1`, `0.0.0.0` or `[::1]` with a port; the last one found becomes a chip `:5173 ↗` in the pill that opens `http://localhost:5173` in the browser, and goes when the command ends.
- **Find** shows `3 of 41` (xterm's result counter), ⌘G and ⇧⌘G go to the next and previous match also with the bar closed (for the last query), and the matches are marked on the terminal's overview ruler.
- **Recent commands** (⌘R): the last 200 commands of this session (from `pty.command`, newest first, a repeat moves up) in a palette-like list through `safeCommand`; Enter copies the raw command and says so. Nothing is typed, and the list is in memory. Since 1.2.0 each entry also remembers the folder the command ran in (`RecentCommand.cwd`: the shell's folder when the command's end mark arrived, redacted and cut like the command, memory only; a repeat takes the newest) and a *By folder* toggle (`groupByFolder`, pure: groups under the `~` path, the newest folder first, an *Unknown folder* group last) shows the folders as headers; the rows follow the grouped order, copying is unchanged.
- **The shortcuts sheet** (⌘/, 1.2.0): the overlay kind `keys` (`ShortcutsSheet`): `shortcutGroups` (`src/shared/shortcuts.ts`) lists every keyed palette action, the menu items with an accelerator that run no palette action (⌘P) and the terminal's own keys (`TERMINAL_KEYS`, a test keeps them equal to the terminal's key handler), grouped by the palette's sections, each key once, with a search over title, keys and section; Esc closes it. The menu item (*Help → Keyboard Shortcuts*) carries the accelerator, the page's own key handler does not, so one press cannot toggle twice. Role items (copy, paste, quit, full screen) are not listed.
- **Pins** (⇧⌘L): the first line of the selection (redacted, 200 characters) is pinned in a strip at the top of the card; at most 3 (the oldest goes), each with a ×. `.terminal-area` clips rather than hides its overflow because a pin strip appearing used to scroll the card itself.
- **Column ruler** (`terminal.ruler`: 0, 80, 100 or 120) is a faint line placed from the measured cell width. **Images** (`terminal.images`) switches xterm's image addon (sixel, iTerm inline images) on or off at runtime; Kitty graphics are not supported (the addon has none).

## Focus mode, themes and blur

- **Focus mode** (⌥⌘F, the palette): the window fades the title bar, the tool strip, the pins and the companion to 15 % and tells main (`jaffer:focus-mode`). `FocusHold` in main holds notifications of five kinds (Claude needs you, Claude finished, a command finished, a command failed, a terminal notification) and the needs-you Dock bounce, counting them by kind only (never what they said), and drops the bell's Dock bounce. Ending it shows one notification, `While you were focused: Claude finished twice, 1 command failed`, when anything was held. The update prompt's notice is never held. It is session state: it ends with a closed window or a reload. ⌃⌘F is not used: it is macOS's Full Screen, held by Electron's own menu role.
- **Auto theme** (`appearance.autoTheme`: `off`, `system` or `time`): `resolveTheme` (`themes.ts`) picks `appearance.lightTheme` in macOS's light appearance (`prefers-color-scheme`, followed live) or from 07:00 to 19:00 local time (the hour is looked at every 5 minutes), else `appearance.theme`. A change of the resolved theme crossfades for 1 s (`.theme-fade`; the terminal's own colours switch at once; none with Animations off, shorter under Reduce motion).
- **Blur** (`appearance.blur`): main sets `win.setVibrancy` from `vibrancyFor(config)` at the window's creation and only when the setting changes (`appearanceChanged`); with it off the surfaces are opaque whatever the opacity slider says (`windowOpacity`).
- **Settings → Claude Code → hooks** lists the eleven always-installed events (the optional twelfth is never reported as missing) with "last seen 3m ago" or "not seen yet" (`claude.hooks`, refreshed every 10 s while the page is open), and warns when a `SessionStart` was seen but no `Stop` since for over an hour while no session is working.
- **The menu's labels and accelerators** live in `src/shared/menu-spec.ts`; `test/menu-spec.test.ts` keeps them, the palette's actions and every key unique (and away from Full Screen's).

## Config

`~/.jaffer/config.json`, read by the daemon (`ConfigStore`): `onboarded`, `appearance.*` (theme, `autoTheme`, `lightTheme`, font, opacity, `blur`, `glow`, `seasonal`, `systemStats`, cursor, scrollback, renderer, animations, companion, `petSize`), `shell`, `window.*` (`closeAction`, `menuBar`, `menuBarOnly`, `menuBarTitle`, `hintShown`, `dropdown`), `claude.*` (`skipped`, `showCost`, `liveCost`, `dailyBudgetUsd`, `toolStrip`, `turnSummary`, `approvals` (the opt-in permission prompts) and `typicalTurnMs`, which the daemon keeps and Settings does not show), `terminal.*` (`blocks`, `pasteGuard`, `ruler`, `editorUrl`, `images`, `portLinks`), `panel.*` (`open`, `width`: the side panel), `history.*` (`names`, `pinned`, and since 1.4.0 `tags` and `hidden`: the person's own labels, pins, tags and hidden ids for past conversations, lists of text), `permissions.*` (1.4.0: `explain`, `deepSearch`, `resumeTyping`, `trash`), `tour.done` and `tips.*` (`enabled`, `seen`), `claude.dailyWorkBudgetMin`, `claude.projectBudgets`, `notifications.weeklyDigest` and `usage` (numbers and ISO week ids: this and last week's `{id, usd, workMs}` and `digestWeek`), `updates.auto`, `updates.seenVersion` (the newest version whose release notes were dismissed), `notifications.claudeFinished`, `session.stayAwake`, `hotkey` and `migrated`. On load and on every patch a value takes the kind of its default (a section stays an object, a switch a boolean, a list a list of text), and one that does not fit keeps what was there; keys the defaults do not list (a newer version's, or a removed setting before the first start's clean-up prunes it) pass through and nothing reads them. `jaffer config set` says when it refused a value.
