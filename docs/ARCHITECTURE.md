# Architecture

```
┌────────────────────────── Jaffer.app (Electron) ───────────────────────────┐
│ main process: window, menu, dock, notifications, global hotkey, updates,    │
│               the quit question, IPC relay, the first-start clean-up        │
│ renderer: Preact + xterm.js (WebGL) · companion · command palette           │
└───────────────▲───────────────────────────────────────┬─────────────────────┘
                │ unix socket (NDJSON RPC + events),    │ starts it as its CHILD (JAFFER_OWNED=1,
                │ ~/.jaffer/run/jafferd.sock            │ a pipe on its stdin: the pipe ends = stop)
┌───────────────┴──────────── jafferd (the app's child) ▼─────────────────────┐
│ SessionHost ── PtySession ── node-pty ── your login shell (zsh/bash/fish)   │
│     │             └ headless xterm: screen snapshots, OSC 133/633 parsing    │
│ ClaudeWatcher ── live state of the terminal's Claude, from its hook events   │
│ cost reader · transcript watch · StayAwake (caffeinate) · config             │
└───────────────▲─────────────────────────────────────────────────────────────┘
                │ same RPC
   jaffer CLI ──┴── `jaffer hook <event>` (run by Claude Code, inside Jaffer's terminal only)
```

There is one process tree and it has one owner: the app. Quitting the app ends the shell and anything running in it.

## The app owns the session

The terminal host, `jafferd`, is a separate process (the PTY and the headless terminal stay off the Electron main thread, and the hooks and the CLI reach it over a socket), but it is the app's **child**, not a background service. `startOwnedDaemon` (`src/core/daemon-client.ts`) spawns it with the app's own binary as `ELECTRON_RUN_AS_NODE=1` (no separate Node install), not detached, with `JAFFER_OWNED=1`, `JAFFER_HOME`, `JAFFER_CLI_SCRIPT` and a pipe on its stdin that the app holds and never writes; its stdout and stderr go to `~/.jaffer/run/jafferd.log` (rotated at 5 MB).

- **How it ends.** The daemon reads `JAFFER_OWNED` and deletes it from its own environment at once (`src/daemon/main.ts`; `JAFFER_OWNED` is also stripped from what the shell gets, so nothing it starts sees it). Once it listens, `watchParent` (`src/daemon/shutdown.ts`) takes the end of its stdin, however it comes (the app quits, crashes or is SIGKILLed: the system closes the app's end of the pipe), as the cue to stop: the shell is let go, the socket removed, exit code 0. The flag is opt-in: the tests, `ensureDaemon` and the dev bridge start the daemon detached with `stdio: 'ignore'` (`detachedSpawnArgs` removes the flag from the environment), and such a daemon runs until `app.shutdown` or a signal.
- **Exit codes** (`src/daemon/shutdown.ts`): 0 for a deliberate end (`app.shutdown`, the end of the app's pipe), 143 for SIGTERM and 130 for SIGINT; anything else is a crash. SIGHUP is ignored. The first reason wins (a second signal, or one during `app.shutdown`, neither exits early nor turns 0 into 143), and a stop that hangs ends at an 8 s deadline.
- **Only its own child.** `startOwnedDaemon` connects to the socket only when `hello.pid` is the child's pid; if another daemon already holds the socket, the child finds it taken and exits 0, and the start fails fast instead of taking someone else's session. A child that does not answer in 12 s is killed and the start fails ("Jaffer could not start its terminal", then the app quits).
- **Quitting.** `⌘Q` (or the Dock's Quit) goes through `before-quit`: when Claude Code is working or waiting for the person (the hook state), or the running command is `claude`, or any command runs (the shell's own marks: `pty.start` / `pty.command`, and `session.info.busy` at connect), a native question asks first (`quitNeedsConfirm` in `src/shared/quit-policy.ts`: *Quit Jaffer?* with *Claude Code is running and will stop.* or *A command is running and will stop.*, **Quit** / **Cancel**, Return and Esc mean Cancel; a sheet on the window when it is visible). A shell without Jaffer's marks (`/bin/sh`) or a background job is not seen, so nothing is asked for those. Nothing is asked for an update (its own prompt said so), Reset, a session that already ended, or when nothing runs. Then `will-quit` calls `OwnedDaemon.stop(3 s)`: the pipe is ended, the child gets 3 s, then SIGKILL, then the app exits. `⌘W` only hides the window (the hotkey, the Dock or `activate` brings it back).
- **The child ends by itself** (`childExitAction`): exit 0 on its own is a session a client ended on purpose (`jaffer reset`, `jaffer daemon stop`): the app quits with it, without a question. Anything else is a crash: the window says *The terminal stopped.* and a native dialog offers **Restart terminal** (a fresh child, a fresh shell; the window re-attaches on `daemon.up`) or **Quit**. If the connection closes while the child still runs, the app waits 1 s for its exit, reconnects to the same pid for up to 5 s, and kills the child if it cannot be reached (which ends in the crash dialog).
- **Only the first instance runs.** `requestSingleInstanceLock`: a second app (opened from a disk image while the installed copy runs, `open -n`) calls `app.exit(0)` at once and starts nothing (the whole start is behind `gotLock`: it would find the first instance's own terminal on the socket and offer to end it); the first instance brings its window forward, once its start has made one.

### The start, in order (`whenReady`, `src/main/main.ts`)

1. The single-instance lock (above), then the menu.
2. **An older Jaffer's background session.** Before 0.6.0 the daemon outlived the app; after installing over a running one it may still hold the socket. When anything answers there (`legacyDaemonAction`), a native dialog asks once: *Another Jaffer session is running in the background. Jaffer no longer keeps sessions running. End it and start a fresh terminal?* **End it** / **Quit** (Return and Esc mean Quit). End it sends `app.shutdown` (every older version knows it) and waits up to 10 s for the socket to go; if it stays, an error says to quit the other Jaffer process in Activity Monitor or restart the Mac, and the app quits.
3. **`prepareHome`** (`src/main/prepare-home.ts`): the first-start clean-up of an upgraded Mac (below), never throwing and bounded at 30 s.
4. **The terminal**: `startOwnedDaemon`, connect, read the settings (the hotkey).
5. The window, the Dock's `activate`, the updater, and under `JAFFER_SMOKE=1` the smoke test (which also checks that `hello.pid` is the app's own child).

## One session

There is one shell, and the code makes it the only one: `SessionHost` runs a single `PtySession` (`main`), refuses to spawn any other, and the daemon has no RPC to open or close one (`pane.list` only reports it). The UI has no tabs, splits or extra windows. A start is a plain shell in the home folder with a blank screen. **Nothing of the terminal is saved or replayed**: if the shell exits (`exit`, a crash, *Restart shell*) the host starts a fresh one in the folder the old one was in, with a blank screen, after a short wait that doubles (up to 10 s) while shells die within seconds of starting. The window is told to start over from the new shell's blank screen (a `pty.reset` to every attached client, `resyncAttached`), because the new shell's output counts from 1 again. 0.5.x saved the screen and replayed it into the new shell, which could replay a dead program's terminal modes (mouse reporting) into a fresh shell; with the saved screen gone, that is gone too.

## Terminal fidelity and re-attach

PTY output is parsed by a headless xterm.js in the daemon *before* it is emitted to clients. A client attaches with `session.attach`, which waits for the write queue to drain and returns `serialize()` output (screen + scrollback + alt-screen + modes) plus a sequence number; every later `pty.data` event carries `seq`, so the renderer drops anything already covered by the snapshot and re-attaches on any gap (the window re-attaches when its page reloads, for instance). Slow clients are resynchronised from a snapshot (`pty.reset`) instead of buffering without bound.

Shell integration scripts (`resources/shell`, embedded into `src/generated`) hook zsh (`ZDOTDIR` shim that sources your real dotfiles), bash (`--init-file`, bash 3.2 compatible) and fish. They emit OSC 133 (`A` prompt, `C` output start, `D;<exit>`) and OSC 633 (`E` command line, `P;Cwd=`). From those the daemon knows what ran, with what exit code, for how long and in which folder (`pty.start`, `pty.command`, `pty.cwd`); the title bar, the notifications, the quit question and staying awake follow them. The marks are output, and any program can print them, so nothing that matters rests on them alone, and the command line they carry is read only by helpers that cut it to a head (see *Process boundaries and trust*). The shell gets `JAFFER_SESSION=1` (which switches the hooks on), `JAFFER_HOME`, `JAFFER_SOCK`, `JAFFER_BIN` (the integration scripts put it on the `PATH`, so `jaffer` works) and `TERM_PROGRAM=Jaffer`.

**The daemon types nothing of its own into the shell.** Only what the window sends (`pty.write`: the person's keys and the terminal's own replies) reaches it. The one command the product ever types is `claude`, and the window does it, through its terminal, as the person would: for ⇧⌘C (*Run Claude Code*) and for the first-run switch *Start Claude Code in the terminal now*. Claude Code's own questions (trust a folder, allow a tool) stay in the terminal and Jaffer answers none of them.

## One Claude, and a quiet reflection of it

There is one Claude in Jaffer: the `claude` running in the terminal. Jaffer has no chat of its own and runs no model of its own. The mole (or another scene), the title-bar ring and a desktop notification reflect what Claude Code is doing, fed by Claude Code's own hooks. There is no panel and no chat.

- **Events in.** *Settings → Claude Code → Connect*, the first-run consent and `jaffer setup claude` register hooks in `~/.claude/settings.json` (and a daemon start refreshes them when they already point at its own wrapper): SessionStart, Stop, UserPromptSubmit, PreToolUse, PostToolUse, PostToolUseFailure, SubagentStart, SubagentStop, Notification and SessionEnd. All ten are `async` (Claude Code never waits for them, five seconds at most), guarded by `[ "$JAFFER_SESSION" = 1 ] || exit 0` so they do not even start Jaffer outside its terminal, and tagged `# jaffer-managed` so that only Jaffer's own entries are ever changed or removed. Each runs `jaffer hook <event>` (through `~/.jaffer/bin/jaffer`), which does nothing unless `JAFFER_SESSION=1`, forwards the JSON payload to the daemon as `claude.event`, prints nothing and exits 0 on every path, so Claude Code behaves exactly as without Jaffer when the daemon is down or slow. A `claude` that the daemon runs itself (`claude auth ...`) has `JAFFER_NO_HOOKS=1` and reports nothing.
- **State.** `ClaudeWatcher` (`src/core/claude/watcher.ts`) is a pure state machine per `session_id`: `idle`, `working`, `needs-you` or `ended`, the tool call being run (its name and id, never its arguments), background agents (id, running or done, when they started), Claude Code's own permission wording (`notice`, redacted) and the cost of the answers. It keeps **nothing the person wrote or Claude answered**: no prompt, command, file name, reply or folder, not even redacted, because nothing shows it. Hooks are asynchronous and can arrive out of order, so only UserPromptSubmit and PreToolUse move a session to `working`, a SessionStart that lands late never takes a working or waiting session back to idle, a permission Notification only counts while a tool is pending, and the late result of an earlier overlapping call does not clear a later tool. `sessions()` is the daemon's own view (with the transcript path it reads); `view()` is what leaves the daemon, over the `claude.state` RPC and event, and has no file paths.
- **Staleness.** Declining a prompt or pressing Esc in the terminal fires no hook (and Esc no `Stop`), so while a session is `working` or `needs-you` the daemon reads the tail of its transcript (`transcript-watch.ts`) for the person's own "User rejected tool use" / "[Request interrupted by user" entry (`isStopLine`: the user side only, text starting with the marker, so the same words in code or command output do not count) and calls `ClaudeWatcher.interrupted`. A sweep every 30 s is the safety net for a turn that ended with no signal at all: `working` with no hook for 5 minutes (30 with a tool running) and a transcript that is not growing becomes idle; `needs-you` is never swept. The `claude` command finishing in the shell ends every session (also a crashed Claude Code), unless it was only stopped (Ctrl+Z), and so does the shell itself exiting.
- **Notifications** (the main process, only while the window is not in front): *Claude needs you* when a session newly enters `needs-you` (`notify-policy.ts`; the Dock icon bounces too), *Claude finished* after a turn of 30 s or more (`FinishedNotifier`: it waits up to 2.5 s for the cost of the answer, and stays quiet if the window came to the front, the next turn began, or Claude Code's own terminal notification just fired; `notifications.claudeFinished` turns it off), a command that ran 30 s or more (*Command finished* / *Command failed*, redacted, a sensitive command not named), and the terminal's own notifications (OSC 9 and 777). Claude Code's own terminal notification and Jaffer's never both fire for one event (a 10 s window).
- **Cost.** When `claude.showCost` is on, the daemon notes the size of the transcript at `UserPromptSubmit` and, at `Stop`, reads what was written since (`core/claude/cost.ts`, up to the end it measured, so a response Claude gives later without a prompt is measured from there; where a turn began is kept 10 s past the session's end, because the Stop of a `claude -p` answer can arrive after its SessionEnd). `shared/claude-cost.ts` sums the `usage` of each model response once per message id (Claude Code writes one line per content block, all carrying the same usage) and prices it from a table of Anthropic's list prices (cache reads and 5-minute and 1-hour cache writes separately; fast mode and US-only inference where the model has them). A model id the table does not know exactly (a dated snapshot is fine, `claude-opus-5-6` is not `claude-opus-5`) gets tokens and no dollars, never the nearest price. Only numbers are kept: `ClaudeSession.cost` holds the last answer's tokens and dollars and the session total, in the daemon's memory for as long as the session lives; no text from the transcript reaches the state or the UI. Background agents' own usage is not in the main transcript's totals. The title bar shows it (`CostChip`); the price table is the one thing to update when Anthropic changes prices or adds a model.
- **Sign-in help.** `claudeAuth` asks `claude auth status --json` (only the logged-in flag is read; the account stays inside that function) and `ClaudeLogin` runs `claude auth login`, which opens the browser. Both run with the person's own environment minus `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN`: Jaffer runs on Claude subscriptions only. `findClaude` finds the binary the way the person's shell would (PATH, the usual install folders, then the login shell, 8 s at most). Claude is optional: the first-run step *Use Jaffer as a plain terminal for now* installs nothing and starts nothing and sets `claude.skipped`; connecting clears it.
- **Surface.** RPC `claude.event` (from hooks), `claude.state` (snapshot) and the pushed event `claude.state` (throttled to one per 100 ms). The state lives in the daemon, which lives as long as the app.
- **Not built yet:** answering Claude Code's permission prompts from Jaffer (a blocking permission hook, allow only after a click, any failure leaving Claude Code's own dialog in charge), and diffs from the transcript.

## Staying awake

`StayAwake` (`src/core/session/stay-awake.ts`) is the decision, with its clock, timers and effects injected so the tests need no waiting; `caffeinate.ts` is the one place that touches the Mac: `/usr/bin/caffeinate -i -w <daemon pid>`. `-i` holds off idle system sleep only (never the display) and `-w` ends the hold by itself if the daemon dies (so a daemon that dies cannot leave one behind). The daemon hands it what works: a Claude session `working` or a background agent running, or a command that has run 30 s in the shell and is not an interactive program (`isInteractiveCommand`: `ssh`, `mosh`, `vim`, `less`, `man`, `top`, `tmux`, `watch`, `tail -f`, `claude`, ..., also behind `sudo`, `env`, `nice`, `time`, `nohup` and the like, with their options and the values those take, as in `sudo --user deploy vim`). A Claude that waits for the person (`needs-you`) is not work. The hold is let go 15 s after the work stops, so a pause between tool calls does not flap it; a command alone never holds longer than 6 hours. It releases at once when `session.stayAwake` goes off and when the daemon stops, and does nothing off macOS or for a home that is not the default one (`isDefaultHome`). There is one `caffeinate` at a time; if it ends by itself while the work goes on (killed, crashed, could not start: said once in the log), the hold is taken up again after 1 s, doubling at each end up to 30 s and starting over after a clean minute (`STAY_AWAKE` in `src/shared/stay-awake-config.ts`). It needs no admin rights and does not override the lid: `pmset disablesleep` is not used, and Jaffer never asks for a password. `JAFFER_TEST_HOLD_LOG=<file>` stands in for macOS in the tests (every hold and release is a line of JSON in the file).

## The first start on a Mac an older Jaffer ran on

0.5.x kept a background session, a login agent, a saved screen and a memory. 0.6.0 keeps none of them, and takes away what they left, once. `migrateToPlainTerminal` (`src/core/migrate.ts`, called by `prepareHome` after an older session has been ended and before the child starts) runs when `config.json` has no `migrated: 1`; every later start reads that one file and does nothing. In the order it runs, each step on its own:

1. `agent` — `removeLegacyAgent` (`src/core/service/legacy-agent.ts`): the login agent's plist (`~/Library/LaunchAgents/com.jafforge.jaffer.daemon.plist`), its wrapper (`~/.jaffer/bin/jafferd`) and its job in launchd (`launchctl bootout gui/<uid>/com.jafforge.jaffer.daemon`, 20 s at most, then SIGKILL; a job launchd does not know is the usual case). The reason it is first: an agent left behind would start a daemon of its own, or fail every five seconds if the app it names moved. The wrapper names `dist/daemon/jafferd.cjs`, which is why that file never moves. `JAFFER_NO_LAUNCHCTL=1` skips the `launchctl` call.
2. `backup` — `memory/NOTES.md` and `memory/POLICY.md` are copied to `~/.jaffer-memory-backup/` (a private 0700 folder, files 0600, never over something there: `NOTES-2.md`...) when they hold anything of the person's: a regular file, not blank, and a `POLICY.md` that is not still exactly the text every older version seeded.
3. `oldData` — `memory/`, `session/` and `bin/jafferd` are deleted (the memory only once its backup is made; if the backup failed it stays and the log says so). A link is removed, never followed.
4. `claudeMd`, `skills`, `firstDayBlocks` — Jaffer's marked block is taken out of `~/.claude/CLAUDE.md` (and, from the first builds, `~/.codex/AGENTS.md` and `~/.gemini/GEMINI.md`), everything else in the file byte for byte (a file that held only the block is deleted); and the `~/.claude/skills/jaffer-*` folders whose `SKILL.md` carries Jaffer's marker line (the person's own `jaffer-…` skills stay). The exact markers are in `src/core/integrations/legacy-claude.ts` and never change.
5. `config` — the settings 0.6.0 no longer has are pruned from `config.json` (`DEAD_KEYS`: `memory`, `ingest`, `export`, `safety`, `session.restoreScreen`, `session.resumeClaude`, `session.keepRunning`, `session.autoResume`; every other key, unknown ones included, stays) and `migrated: 1` is written, whatever the steps before did: a step that failed is not retried at every start. A `config.json` that cannot be read as settings is kept as `config.json.unreadable`. A start that was ended before this step (the app quit while `launchctl` was asked) has not set the marker and runs everything again; every step is safe to repeat.
6. `mcp` — `claude mcp remove jaffer -s user` (10 s at most; `claude` is looked for only now, only when an older Jaffer folder existed, so a fresh install runs no `claude`). It exits non-zero when no such server was registered, which the log records as `failed` with both readings.

The hooks are not touched here: the child rewrites Jaffer's own (`# jaffer-managed`) at its start when they already point at its wrapper, so a 0.5 install's SessionStart and Stop become async and silent.

- **Bounds and safety.** The whole thing gets 30 s (`prepareHomeBounded`) and never throws. A failing step is a line in `~/.jaffer/migrate.log` (the step's name and an error code or a few words, never a path) and the others still run; the log also says `started` first, so an interrupted start leaves a trace. Nothing at all is done in a folder `assertJafferHome` does not accept (the home folder or a parent of it, the root, a code checkout, a folder without "jaffer" in its name, or one that holds files but none of Jaffer's own; links are resolved first: a `~/.jaffer` that is a link to the home folder is refused, and one that is a link must point at a folder named like Jaffer's).
- **Only for the person's own folder.** What lies outside `~/.jaffer` (steps `agent`, `claudeMd`, `skills`, `firstDayBlocks`, `mcp`) is touched only when the home is the default one (`isDefaultHome`, which also requires `$HOME` to be the system's home for the user): a smoke test or a dev run with another `JAFFER_HOME` cleans inside that folder only and leaves the person's Claude Code and launchd alone. It still deletes `memory/`, `session/` and `bin/jafferd` inside the folder it was given: never point the app at a real `~/.jaffer` to look at it.
- **Run it again** with `jaffer config set migrated 0` (a fresh start then repeats it).
- **Reset** (`src/core/reset.ts`, *Settings → Reset* and `jaffer reset`) runs the same cleanups on request and more: the login agent, then the session ends (`endSession`: the app stops its child; the CLI asks the daemon to `app.shutdown`), Jaffer's hooks (the person's own stay), the MCP server, the blocks and skills above, the `~/.local/bin/jaffer` link when it points into Jaffer's folder, the update cache, the app's own data (`jaffer reset` removes Electron's folders and preferences; the app's Reset clears its own storage and cache and the login item) and `~/.jaffer` itself, moved aside as `~/.jaffer.backup-<time>` unless the person chose to delete it; the app then relaunches as a fresh install. Claude Code itself, its login and the person's own settings stay. Reset judges the folder with `assertJafferHome` too; for a `~/.jaffer` that is a link it renames or removes only the link, never what it points at. `jaffer reset` refuses to run inside Jaffer's own session (it would end the terminal it was typed in); the app's Reset asks in its own dialog first.
- **The legacy modules** (`legacy-claude.ts`, `legacy-agent.ts`) are the only code that still knows about the removed features, and only to take their leavings away. They hold the exact text and names older versions used (the block markers, the skill marker line, the launchd label and the plist path), which is why those must not change; remove them when no Mac that ran 0.5 or earlier can still be upgraded.

## The command line

`jaffer` runs against the app's terminal and never starts one: with no app running, `status` and `doctor` say so, and `daemon start` and `setup claude` fail with *Jaffer is not running. Open Jaffer and run this again.* The commands are `hook <event>` (Claude Code's; above), `setup claude [--remove|--status]` (the hooks, nothing else: it needs the wrapper `~/.jaffer/bin/jaffer`, which the daemon writes at its start), `status` / `doctor`, `config get|set <dot.path> <json>` (a value of the wrong kind is refused and the command says so), `daemon [status|stop]` (`stop` ends the terminal, and the app quits with it), `reset [--yes] [--delete]` and `--version`. Inside Jaffer's terminal `jaffer` is on the `PATH`; elsewhere *Install the `jaffer` command* from the palette links `~/.local/bin/jaffer`.

## Process boundaries and trust

The renderer is sandboxed (`contextIsolation`, no Node) and only reaches the daemon through the preload bridge; the main process checks the sender frame. Everything the watcher, the notifications or the window show from a hook payload or a command is redacted first (`src/shared/redact.ts`), and a sensitive command (`isSensitiveCommand`) is not named at all.

- **The window shows one page.** `shared/window-policy.ts` (`isAppUrl`) is used by `will-navigate` and by the IPC sender check: a file dropped on the window, or a link, never navigates it to a page that would then get the preload bridge (and with it a shell to type into). The `reveal` IPC opens Jaffer's own folder only; `openExternal` takes http(s) only.
- **A program may copy, not read.** The terminal answers OSC 52 *write* requests (so `ssh` can fill the clipboard) but never a *read* request (`osc52Provider`): whatever you last copied is not for the program that printed the query.
- **The redactor and the command-line helpers are on the hot path.** They run on the daemon's main thread over untrusted text (command output, forged marks), which also relays the terminal. Every redaction rule is bounded (no unbounded run of characters before a literal); `test/redact.test.ts` holds timing tests, because one unbounded rule once took 10 s on 9 KB. The helpers that read a command line (`isClaudeCommand`, `isInteractiveCommand`) slice their input to the `COMMAND_HEAD` (4096-character) head themselves, because the line comes from the shell's marks and can be forged at any length, and the window reads it too; timing tests feed them 1 MB and 8 MB crafted lines (unbounded patterns used to throw `RangeError` at about 8 MB).
- **Files of the user's own** (`~/.claude/settings.json`, `~/.claude/CLAUDE.md`) are written through a symlink and keep their permissions (`writeFileAtomic(..., { preserve: true })`); only hooks tagged `jaffer-managed` and skills carrying Jaffer's marker line are ever removed; `reset` and the first start's clean-up refuse a folder that is a code checkout or holds none of Jaffer's own files.
- **What Jaffer keeps on disk**, in `~/.jaffer` (the folder is private, 0700, and the socket is 0600 in a 0700 folder): `config.json`, `window.json` (the window's place), `run/` (the socket and `jafferd.log`), `shell/` (the integration scripts), `bin/jaffer` (the wrapper that hooks and the CLI run), `updater.log` and, after a first start on an upgraded Mac, `migrate.log`. No screen, scrollback, command history, command output or transcript text is written. In `~/.claude/settings.json` only the `# jaffer-managed` hook entries; `~/.local/bin/jaffer` only when asked.

## Updates

`src/main/updates.ts` (`UpdateController`) drives `electron-updater` against the GitHub releases and decides nothing about the outside world itself: the updater, the dialog and ending the session are injected, so it is tested with fakes (`test/update-controller.test.ts`). `src/shared/update-policy.ts` holds the pure parts (prompt wording, when to ask, version checks, reading `codesign` output). The flow is check → download in the background → **ask** (native dialog: *Updating restarts Jaffer and ends your terminal session: the shell and anything running in it stop, and a fresh terminal starts.*; Claude working is said too; Return and Esc mean *Later*) → on yes, `prepareInstall` stops the app's own child (the shell ends) and the app calls `quitAndInstall`; a watchdog (60 s) or an updater error brings the app back with a fresh terminal and an error dialog. `autoInstallOnAppQuit` is off on purpose: quitting must never replace the app behind a running session. Only a packaged, Developer ID signed app checks (the bundle's signature is read at startup), only non-prerelease releases count, and errors are logged to `~/.jaffer/updater.log` and shown in Settings, never as a dialog unless the user asked. The release side is `scripts/release-mac.sh`: it checks `latest-mac.yml` and uploads it after everything it names.

## The window

The renderer is a terminal card on a canvas, with a thin title bar above (folder, branch, what is running, and the cost of the last answer). There is no sidebar, drawer, status bar or panel. Colours come from layered tokens derived from the active theme (`themes.ts`): `--chrome` is the canvas, `--surface` the card on it, `--raised` things on that. A theme change repaints the whole app. Settings has four sections: Appearance, Claude Code, Updates and Reset; the first run asks about Claude Code and nothing else.

- The title bar reads `session.info` (folder, branch) and keeps itself live from `pty.start`, `pty.command` and `pty.cwd` events. The ring beside the folder is `processBadge` (`src/shared/process-badge.ts`): an ordinary command spins while it runs; Claude Code spins only while its hooks say it is working. The cost figure (`CostChip`) is on the right while `claude.showCost` is on.
- The companion (`Pet.tsx`, `src/shared/pet-mood.ts`) is an SVG in a corner of the terminal card, chosen in Settings → Appearance (`appearance.companion`, listed in `src/shared/companions.ts`; anything unknown is the mole). The mole is the original; the other five are scenes (below). Every pose is a `[data-mood]` state (sleep, rest, dig, alert, cheer), so it is right with Animations off too; the motion is added only under `:root:not([data-motion='off'])` and stops under macOS Reduce motion. It ignores pointer events. A helper mole stands for each running subagent (`ClaudeSession.subagents`, at most three, `src/shared/pet-crew.ts`); a helper whose agent finished cheers for a moment and leaves. Effort grows with time (`src/shared/pet-effort.ts`: 30 s, 2 min, 5 min since the turn or the command started, or since the helper's own `SubagentStart`; `ClaudeSubagent.startedAt`, `info.busySince`): `data-effort` 0–3 sets the digging tempo (`--t`) and adds the sweat drop, the hard hat and a bigger pile, all static under Animations off. Background agents outlive the turn that started them, so `Stop` does not end them: `SubagentStop`, the session ending, or half an hour of silence does.
- The scenes (`Scenes.tsx`, geometry in `src/shared/scene-geometry.ts`): **Matrix** (digital rain, an agent is a brighter coloured column), **Agent network** (a hub and up to three nodes passing packets), **Warp** (a starfield at speed, a wingman ship per agent), **Radar** (a sweep and a blip per agent) and **Reactor core** (counter-rotating rings, equaliser bars, satellites). They take the same inputs as the mole (`petMood`, effort, the crew from `pet-crew.ts`), draw into one 240×80 SVG frame, and follow the same rules: the still pose of every mood is the base style, motion is added only under `:root:not([data-motion='off'])` and ends at once under macOS Reduce motion, colours are theme tokens only (`--ok`, `--info`, `--violet`, `--accent`, `--warn`), and the corner ignores pointer events. Everything that varies (rain columns, star positions, node places) is a pure function in `scene-geometry.ts` with no randomness, so a render is the same every time and `test/scene-geometry.test.ts` can pin it. Settings shows each one live in a radio group (`CompanionPreview`); the effort tempo is the `--t` variable, as for the mole.

## Config

`~/.jaffer/config.json`, read by the daemon (`ConfigStore`): `onboarded`, `appearance.*` (theme, font, opacity, cursor, scrollback, renderer, animations, companion), `shell`, `claude.skipped`, `claude.showCost`, `updates.auto`, `notifications.claudeFinished`, `session.stayAwake`, `hotkey` and `migrated`. On load and on every patch a value takes the kind of its default (a section stays an object, a switch a boolean, a list a list of text), and one that does not fit keeps what was there; keys the defaults do not list (a newer version's, or a removed setting before the first start's clean-up prunes it) pass through and nothing reads them. `jaffer config set` says when it refused a value.
