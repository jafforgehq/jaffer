# Architecture

```
┌────────────────────────── Jaffer.app (Electron) ───────────────────────────┐
│ main process: window, menu, dock, notifications, global hotkey, IPC relay   │
│ renderer: Preact + xterm.js (WebGL) · companion · memory drawer · palette   │
└───────────────▲─────────────────────────────────────────────────────────────┘
                │ unix socket (NDJSON RPC + events), ~/.jaffer/run/jafferd.sock
┌───────────────┴────────── jafferd (detached, survives the app) ─────────────┐
│ SessionHost ── PtySession ── node-pty ── your login shell (zsh/bash/fish)   │
│     │             └ headless xterm: screen snapshots, OSC 133/633 parsing    │
│ MemoryEngine ── EpisodeLog → heuristics / model reflector → MemoryStore     │
│     │              (journal, decay, consolidate, skills, exports)            │
│ ClaudeWatcher ── live state of the terminal's Claude, from its hook events   │
│ ClaudeIngestor · ClaudeLogin / claudeAuth · config                           │
│ AutoResumer (Restart Claude Code) · StayAwake · KeepRunning (login agent)    │
└───────────────▲─────────────────────────────────────────────────────────────┘
                │ same RPC
   jaffer CLI ──┴── jaffer mcp (stdio MCP server for Claude Code) ── hooks
```

## Why a daemon

The shell must outlive the window. `jafferd` is spawned detached by the app (the app's own binary with `ELECTRON_RUN_AS_NODE=1`, so no separate Node install is needed), or, when the person turned on *Keep my session running in the background*, run by launchd through a login agent (see *Keeping the session and Claude running*). The app, the CLI, the MCP server and Claude Code hooks are all just clients of one socket (mode 0600 in a 0700 directory).

## One session

There is one shell, and the code makes it the only one: `SessionHost` runs a single `PtySession` (`main`), refuses to spawn any other, and ignores extra panes an older state file might list; the daemon has no RPC to open or close one (`pane.list` only reports it). The UI has no tabs, splits or extra windows. If the shell exits (`exit`, a crash, *Restart Shell*) the host starts a fresh one in the same folder with the previous screen restored. Only *Quit and End Session* (`⌥⌘Q`) ends it, on purpose.

## Terminal fidelity and re-attach

PTY output is parsed by a headless xterm.js in the daemon *before* it is emitted to clients. A client attaches with `session.attach`, which waits for the write queue to drain and returns `serialize()` output (screen + scrollback + alt-screen + modes) plus a sequence number; every later `pty.data` event carries `seq`, so the renderer drops anything already covered by the snapshot and re-attaches on any gap. Slow clients are resynchronised from a snapshot instead of buffering without bound.

Shell integration scripts (`resources/shell`, embedded into `src/generated`) hook zsh (`ZDOTDIR` shim that sources your real dotfiles), bash (`--init-file`, bash 3.2 compatible) and fish. They emit OSC 133 (`A` prompt, `C` output start, `D;<exit>`) and OSC 633 (`E` command line, `P;Cwd=`). From those the daemon knows when the shell is idle, what ran, with what exit code and output, and whether it is at a prompt with an empty line. The marks are output, and any program can print them (a remote shell over ssh with an integration of its own, such as fish 4), so they alone never decide that the daemon types: it types anything of its own (`claude --resume <id>` for a Restart Claude Code the person confirmed, see below) only at a prompt with an empty line where the terminal's foreground process group is the shell's own pid (`PtySession.foregroundIsShell`, read with `ps`; anything it cannot read is a no; see *The foreground check*), checked when it decides and asked of the system again the moment it types. There is no way to run an arbitrary command in the shell.

## One Claude, and a quiet reflection of it

There is one Claude in Jaffer: the `claude` running in the terminal. Jaffer has no chat of its own and runs no model of its own (memory curation goes through `claude -p`, on the user's Claude login). The mole, the title-bar ring and a desktop notification reflect what Claude Code is doing, fed by Claude Code's own hooks. There is no panel and no chat.

- **Events in.** `jaffer setup claude` (or the first-run consent, or a daemon start with an older install) registers hooks in `~/.claude/settings.json`: SessionStart and Stop (which feed memory, so Claude Code waits for them) and, `async`, UserPromptSubmit, PreToolUse, PostToolUse, PostToolUseFailure, SubagentStart, SubagentStop, Notification, SessionEnd. Each runs `jaffer hook <event>`, which does nothing unless `JAFFER_SESSION=1` (the shell Jaffer hosts exports it), forwards the JSON payload to the daemon as `claude.event`, prints nothing and exits 0 on every path, so Claude Code behaves exactly as without Jaffer when the daemon is down or slow.
- **State.** `ClaudeWatcher` (`src/core/claude/watcher.ts`) is a pure state machine per `session_id`: `idle`, `working`, `needs-you` or `ended`, the tool call being run (its name and id, never its arguments), background agents (id, running or done, when they started), Claude Code's own permission wording (`notice`, redacted) and the cost of the answers. It keeps **nothing the person wrote or Claude answered**: no prompt, command, file name, reply or folder, not even redacted, because nothing shows it. Hooks are asynchronous and can arrive out of order, so only UserPromptSubmit and PreToolUse move a session to `working`, a permission Notification only counts while a tool is pending, and the late result of an earlier overlapping call does not clear a later tool. `sessions()` is the daemon's own view (with the transcript path it reads); `view()` is what leaves the daemon, over the `claude.state` RPC and event, and has no file paths.
- **Staleness.** Declining a prompt or pressing Esc in the terminal fires no hook (and Esc no `Stop`), so while a session is `working` or `needs-you` the daemon reads the tail of its transcript (`transcript-watch.ts`) for the person's own "User rejected tool use" / "[Request interrupted by user" entry (`isStopLine`: the user side only, text starting with the marker, so the same words in code or command output do not count) and calls `ClaudeWatcher.interrupted`. A sweep every 30 s is the safety net for a turn that ended with no signal at all: `working` with no hook for 5 minutes (30 with a tool running) and a transcript that is not growing becomes idle; `needs-you` is never swept. The `claude` command finishing in the shell ends every session, which also covers a crashed Claude Code.
- **Resume.** Hooks tell `ResumeStore` (`core/claude/resume.ts`, `session/claude.json`, mode 0600) which conversation is alive: its id, the folder it began in, its transcript path and when it was last seen, nothing of what was said. `SessionEnd`, or the `claude` command exiting 0 or by Ctrl+C, forgets it; a crash or a kill, or the daemon stopping, does not (`stopping` ignores the shell dying with the daemon). A shell that exits takes its Claude with it: the daemon ends the watcher's sessions (`endAll`) but keeps the point, and a `SessionEnd` that straggles in right after the shell's exit (`SHELL_EXIT_GRACE_MS`) does not forget it. `claude.resume` offers it only when nothing runs, the shell itself has the terminal (*The foreground check*), the shell is in that folder (compared by real path), it is under two weeks old and its transcript exists; the daemon pushes `claude.resume` whenever that changes. The window shows a button; a click types `claude --resume <id>` (`isSessionId` checks the id where it is stored and where it is typed): that click is how a conversation comes back after a restart, a crash or an update, and nothing resumes by itself (*Resuming a conversation*, below). `session.resumeClaude` turns it off, and turning it off forgets what was kept. A conversation that ended is remembered as ended (the last 50 ids, in memory only): the hooks after a tool call are asynchronous and one can arrive after the exit, and it must not write the point back; only that conversation's `SessionStart` (`claude --resume`) takes it back. `claude --version` or `claude mcp list` finishing is not a conversation ending (`endsConversation`) and leaves a waiting offer alone.
- **Finished.** `FinishedNotifier` (`shared/finished-notifier.ts`, in the main process) fires when a session goes from working to idle after a turn of 30 s or more (`ClaudeSession.turnStartedAt`, which survives a wait for permission), waits up to 2.5 s for the cost of the answer, and stays quiet if the window is in front, the next turn began, or Claude Code's own terminal notification just fired. `notifications.claudeFinished` turns it off.
- **Cost.** When `claude.showCost` is on, the daemon notes the size of the transcript at `UserPromptSubmit` and, at `Stop`, reads what was written since (`core/claude/cost.ts`, up to the end it measured, so a response Claude gives later without a prompt is measured from there). `shared/claude-cost.ts` sums the `usage` of each model response once per message id (Claude Code writes one line per content block, all carrying the same usage) and prices it from a table of Anthropic's list prices (cache reads and 5-minute and 1-hour cache writes separately; fast mode and US-only inference where the model has them). A model id the table does not know exactly (a dated snapshot is fine, `claude-opus-5-6` is not `claude-opus-5`) gets tokens and no dollars, never the nearest price. Only numbers are kept: `ClaudeSession.cost` holds the last answer's tokens and dollars and the session total; no text from the transcript reaches memory, the state or the UI. Background agents' own usage is not in the main transcript's totals. The title bar shows it (`CostChip`); the price table is the one thing to update when Anthropic changes prices or adds a model.
- **Surface.** RPC `claude.event` (from hooks), `claude.state` (snapshot) and the pushed event `claude.state` (throttled to one per 100 ms). The state lives in the daemon, so it survives quitting the app. When a session newly needs the user and the window is not in front, the main process shows a notification (`notify-policy.ts`), unless a terminal notification was just shown.
- **Not built yet:** answering Claude Code's permission prompts from Jaffer (a blocking permission hook, allow only after a click, any failure leaving Claude Code's own dialog in charge), and diffs from the transcript.

## Keeping the session and Claude running

Each part is a pure decision with its clock, timers and effects injected, so the tests need no waiting and no real launchd.

### Resuming a conversation: a click

After a restart, a crash, an update or a reboot the shell and its Claude are gone, and the daemon types nothing by itself: the **Resume Claude** button is the way back, and a click on it is the person typing `claude --resume <id>`. The one other way is Restart Claude Code (below), which the person confirms in a native dialog. 0.5.0 typed it by itself; 0.5.1 removed that, with its setting (`session.autoResume`: an old config file that still lists it keeps it, and nothing reads it) and everything that only served it. An old `claude.json` with an `attempts` block is read and the block is left out at the next write.

- **The offer and the click.** The daemon's `resumeOffer()` is `ResumeStore.offer` (nothing running, the shell in the folder the conversation ran in, under two weeks old, its transcript present, *Offer to resume* on) unless the shell is alive and does not have the terminal. It is pushed as `claude.resume` whenever it changes (a prompt, a command beginning or ending, a conversation beginning or ending, a setting). The window shows the button only while nothing runs, and `resumeClaude` (`src/renderer/actions.ts`) types the command into the terminal like the person would, with `isSessionId` checked again right before. Those pushes follow the marks: a shell that prints none (`/bin/sh`, any shell besides zsh, bash and fish, one that `exec`s into tmux or another shell from its startup file) gives no event when a program starts, so nothing works the offer out again and the window keeps the button it had. So a click asks first: `claude.resume` with `fresh: true` reads the foreground at that moment (never an answer kept from before the program took the terminal), and the window types only when the answer is the conversation it showed. Otherwise it types nothing and shows the answer instead: no button, with *A program has the terminal, so Claude Code was not resumed.*, or the other conversation's button. An error types nothing and leaves the button. A daemon from before this ignores `fresh` and answers as before.
- **The foreground check.** `ForegroundCheck` (`src/core/session/terminal.ts`, behind `PtySession.foregroundIsShell`) answers whether the shell itself has the terminal. The prompt marks cannot say: they are output, and any program can print them (a remote shell over ssh with an integration of its own, such as fish 4). The authority is the terminal's foreground process group, read with one `ps -o tpgid=` call: it is the shell's own pid at its prompt, and a command, a script or a subshell each run in a group of their own. Whatever cannot be read, or not within 500 ms, is a no. The shell's name is not compared (`SHELL=/bin/sh` runs bash and a wrapper shell has a name of its own: the button used to hide for both). An answer is reused for at most 250 ms and is dropped whenever the terminal prints anything (a program that took the terminal prints, and its marks are output), because the daemon asks about six times per command while a conversation is offered, each a synchronous `ps` on its main thread. The moment Restart Claude Code types it asks the system again (`fresh: true`, in `shellChecks`): a cached yes there could type into a program. Bash runs the person's own `PROMPT_COMMAND` just after the prompt mark, which may put a program in the foreground for a moment, so a prompt whose shell does not have the terminal yet is looked at again for up to 2 s (`settleAfterPrompt`).
- **Where the button can still show while a program has the terminal.** In zsh, bash and fish the button follows what runs. In a shell without marks it can stay while a program runs (above), and the click's fresh ask types nothing then. What neither the marks nor the foreground tell from the shell at its prompt is a program in the shell's own process group: one the shell replaced itself with by `exec` keeps the shell's pid (the old name comparison caught it), and a shell with job control off (`set +m`) runs its commands in its own group. In zsh, bash and fish the marks still say a command runs, unless that program prints prompt marks of its own; in other shells nothing tells them apart. The result is the button, and a click on it types into that program.

### Restart Claude Code

The palette entry *Restart Claude Code, to use an update* and the button in *Settings → Claude Code* both go through the main process (`jaffer:restart-claude`), which asks `claude.restart.plan` (`resumable`, `busy`) and shows a native confirmation (`restartClaudeText`: always asked, because it ends whatever runs in the shell; it says when no conversation would come back, and when Claude is working). On Restart it calls `claude.restart`: the daemon notes the conversation it would resume *before* restarting (the shell's exit ends the watcher's sessions), restarts the main shell in the same folder (`restartMain`), and holds the request (`restartHold`: that conversation's id, the pane it was asked in, 30 s). At each prompt of the new shell, not the old one, `restartCheck` makes `check({ explicit: true })` on the `AutoResumer` (`src/core/claude/auto-resume.ts`; its decision is the pure `nextStep`: `idle`, `announce`, `wait` or `type`). That is the only call that starts anything, and `check` without the request does nothing. The new shell has no old background jobs and no half-typed line to mislead it. With no conversation to bring back it is a plain shell restart, and so it is in a shell that prints no marks (`PtySession.shellKind` `other`: any shell besides zsh, bash and fish), which never says when the new shell's prompt is there: `restartPlan` reports nothing resumable, the question says it only restarts the shell, and the Resume button offers the conversation afterwards (asked again at its click). It does not detect that an update is waiting, type anything into Claude's own prompt, or restart the daemon.

- **Announced and cancellable.** `claude.autoresume` `{ state: 'pending', id, typesAt }` goes to the window (the RPC and event names are those of 0.5.0), which shows a toast with a Cancel (`claude.autoresume.cancel`); nothing is typed before `typesAt` (3 s) and not before the person has been quiet for 2 s. A window that connects after the notice began asks `claude.autoresume.state`. With no window it proceeds after the notice. The event then becomes `typed` or `cancelled`, once. The notice, and the request with it, ends without typing when the person types (the key sits in the shell's line: see the next point), when another conversation is offered or the offer goes (a command begins, *Not now*, *Offer to resume* off), when the shell dies and when the daemon stops; the Resume button is left.
- **The line-started rule.** What is typed must never be added to a line the person began. `inputSeq` counts the keystrokes written to the main pane (bar the exemption below), and `lineEmptyAt` is that count when the shell's line was last known to be empty (the pane was spawned, or a command began). `promptReady` holds only when the pane is at a prompt (OSC 133), the shell itself has the terminal (*The foreground check*), and the two are equal: a key typed while the shell reads its startup file, or typed ahead while a command runs, sits in readline's buffer and bash and zsh would put `claude --resume` after it. Otherwise it waits for the next prompt or ends. The exemption: keys written while an interactive `claude` conversation is the running command (`isClaudeCommand && endsConversation && !isPrintMode`) do not count, because they went to Claude, not to the shell's line; counted, anything typed into Claude would stop the restart's resume for good. `claude update`, `--version`, `mcp` and `-p` read nothing from the terminal, so keys typed during them do count. What the daemon types is not "the person typing": it does not move `lastInputAt`.
- **The hold.** It ends when it is typed, cancelled, stale (30 s: a shell with a heavy startup file is given that long for its first prompt), when another conversation is offered or the offer goes, or when the daemon stops.
- **Never after a deliberate end.** A conversation the person ended is not offered, so there is nothing to type for it: `claude` exiting 0 or by Ctrl+C (`endsConversation`: not `claude --version` or `claude mcp ...`), `SessionEnd` (but not one whose `reason` is `other`: Claude Code stopped from outside, by a logout or a shutdown that reached it before the daemon, is offered again after the reboot), *Quit and End Session*, a print-mode run (below), *Offer to resume* off. Ctrl+Z (exit 145 to 150) is a stop, not an end. A non-zero exit is a crash, and the conversation stays offered.

### One Claude

When two Claude conversations are active at once (`twoRunning`, `src/shared/one-claude.ts`; background agents do not count) the window says so once per set of conversations, and only for a set still running 1.5 s later (`TwoRunningNotice`: with `/clear` the new conversation's SessionStart can arrive before the old one's SessionEnd): *Two Claude conversations are running. After a restart the Resume Claude button offers the most recently active conversation.* (A click on it resumes that conversation, as Restart Claude Code does.) A notice, never a kill: Jaffer ends no process the person started.

### Staying awake

`StayAwake` (`src/core/session/stay-awake.ts`) is the decision; `caffeinate.ts` is the one place that touches the Mac: `/usr/bin/caffeinate -i -w <daemon pid>`. `-i` holds off idle system sleep only (never the display) and `-w` ends the hold by itself if the daemon dies. The daemon hands it what works: a Claude session `working` or a background agent running, or a command that has run 30 s in the shell and is not an interactive program (`isInteractiveCommand`: `ssh`, `mosh`, `vim`, `less`, `man`, `top`, `tmux`, `watch`, `tail -f`, `claude`, ..., also behind `sudo`, `env`, `nice`, `time`, `nohup` and the like, with their options and the values those take, as in `sudo --user deploy vim`; the same table `sshHost` reads). A Claude that waits for the person (`needs-you`) is not work. The hold is let go 15 s after the work stops, so a pause between tool calls does not flap it; a command alone never holds longer than 6 hours. It releases at once when `session.stayAwake` goes off, when the daemon stops, and does nothing off macOS or for a home that is not the default one (`isDefaultHome`). There is one `caffeinate` at a time; if it ends by itself while the work goes on (killed, crashed, could not start: said once in the log), the hold is taken up again after 1 s, doubling at each end up to 30 s and starting over after a clean minute (`STAY_AWAKE`). It needs no admin rights and does not override the lid: `pmset disablesleep` is not used, and Jaffer never asks for a password. `JAFFER_TEST_HOLD_LOG=<file>` stands in for macOS in the tests (every hold and release is a line of JSON in the file).

### The login agent and launchd

With *Keep my session running in the background* on (`session.keepRunning`, off by default), launchd owns the daemon. `LaunchAgent` (`src/core/service/launch-agent.ts`) writes two files, each whole (a temporary file renamed over the old one) and talks to launchd through an injected `launchctl`:

- **The plist** `~/Library/LaunchAgents/com.jafforge.jaffer.daemon.plist`: `Label`, `AssociatedBundleIdentifiers` (`com.jafforge.jaffer`: macOS 13 and later name the item after the app in *Login Items → Allow in the Background*, instead of an unidentified script), `ProgramArguments` (the wrapper), `EnvironmentVariables` (`JAFFER_HOME` only; no secret), `RunAtLoad`, `KeepAlive` = `{ SuccessfulExit: false }`, `ThrottleInterval` 5, `LimitLoadToSessionType` `Aqua`, and standard output and error into `~/.jaffer/run/jafferd.log`.
- **The wrapper** `~/.jaffer/bin/jafferd` (mode 0755, so the plist does not change when the app moves): if the app binary it was written for is gone, it is written to delete both files, boot the job out and exit 0 (no test or by-hand run has executed that branch yet); otherwise it exports `JAFFER_LAUNCHD=1` (the daemon reads it once and does not pass it on) and `exec`s the app's binary on the daemon script, with `ELECTRON_RUN_AS_NODE=1` when that binary is Electron's.
- **Exit codes** (`src/daemon/shutdown.ts`): 0 for a deliberate end (`app.shutdown`: Quit and End Session, Update and restart, Reset, `jaffer daemon stop`), 143 for SIGTERM and 130 for SIGINT, all after the state is saved; a crash is non-zero. (Taking the agent away, below, boots the job out, which is launchd's own stop of it.) With `SuccessfulExit: false` launchd restarts every non-zero exit, so a `kill`, `kill -9` or a crash comes back within the throttle, and a deliberate end does not. launchd's own stop at logout, shutdown or `bootout` is not restarted either. The first reason wins (a second signal, or one during `app.shutdown`, neither exits early nor turns 0 into 143), and a stop that hangs ends at an 8 s deadline.
- **Starting.** `launchDaemon` (the app and the CLI) with the plist on disk tries `launchctl kickstart gui/<uid>/com.jafforge.jaffer.daemon` (no `-k`: a job that runs is not touched); if launchd does not know the job, it bootstraps the plist (`RunAtLoad` starts the daemon) and kicks it; only if launchd refuses does it fall back to the detached spawn. The choice follows launchd's answer, never `status()` (a loaded job with no process reads as not loaded). So with the switch on, a plist that is present but a job that is not loaded is loaded and started at the next daemon start, and a manual `launchctl bootout` is undone then: the switch, or `jaffer service remove`, is the control. When launchd took the start but no daemon answers within 6 s (`LAUNCHD_GRACE_MS`) and `launchctl print` shows no process for the job (a daemon that cannot start crash-loops under launchd's throttle; Login Items may not allow it), `ensureDaemon` spawns the daemon detached all the same: its own start rewrites the wrapper, and a launchd instance that comes later finds the socket taken and exits 0. While it waits it also kickstarts again every 2 s (`KICKSTART_AGAIN_MS`): a kickstart that lands while the old daemon is still exiting starts nothing, and without this the wait would end after 12 s with an error. `jaffer service remove` needs no daemon: with none answering it turns the switch off in the config file and removes the agent itself, as Reset does. The wrapper runs the daemon script by its exact path (`dist/daemon/jafferd.cjs` in the app), which therefore never moves.
- **Install policy.** `service.install` in a daemon that launchd does not run writes the files but does not load the job: launchd's own instance would find the socket taken, exit 0, and with `SuccessfulExit: false` nothing would supervise the session. The status then reads `installed` ("active from the next login or restart") and the job is loaded at the next login or the next start through the app or the CLI. In the daemon launchd runs, install only refreshes the files, and `remove` answers the RPC first and boots the job out 50 ms later, which ends that daemon (a deliberate end: launchd does not restart it). At every daemon start, once its socket listens, the plist and wrapper are reconciled with the switch (rewritten when stale, removed when the switch is off, and also removable when the app now runs from a disk image).
- **Refused** (`planAgent`, with the reason shown in Settings and by `jaffer service status`): not macOS; a home other than the real `~/.jaffer` (`isDefaultHome`, so tests and development homes never touch the real LaunchAgents); a path with a control character; an app run from `/AppTranslocation/` or `/Volumes/`; an app run from `node_modules` (a development run).
- **Taking it away.** Turning the switch off, `jaffer service remove`, *Settings → Reset* and `jaffer reset` delete both files and boot the job out (Reset turns the switch off first, so a reconnecting app cannot install it again). When launchd runs the session, that ends it: Settings asks first (every switch-off goes through the main process, which asks the daemon how it stands at that moment and shows a native dialog when it is `running`; the daemon launchd runs always says `running`, with its own pid, whatever `launchctl print` shows), and the CLI prints the same warning; typed in that very session (`JAFFER_SESSION=1`, status `running`), `jaffer service remove` and `jaffer config set session.keepRunning false` change nothing without `--yes`, because the terminal they were typed in ends with the session. A daemon from before 0.5 that cannot say how it stands ("unknown method: service.status") does not reconcile the agent either, so nothing can end and the change goes ahead. `jaffer service [status|install|remove]` reports `not installed`, `installed`, `running (pid)`, `installed but not loaded` or `refused: <why>`.
- **Tests never reach launchd.** `JAFFER_NO_LAUNCHCTL=1` is set for every test run (`vitest.config.ts`, `vitest.e2e.config.ts`) and makes `execLaunchctl` fail at once without running `launchctl`; the agent's tests use a fake `launchctl` and file system, and on macOS lint the generated plist with `plutil` and the wrapper with `sh -n`.

### End Session, print mode and config

- **End Session** is the one end that forgets the conversation: the menu calls `claude.resume.dismiss` and then `app.shutdown` with `forgetConversation: true` (`endSessionCalls`), which forgets the resume point; the first call is there because a daemon from before 0.5 still serving the session ignores `forgetConversation` but knows `claude.resume.dismiss`. Each of the two calls gets 5 s, so a daemon that does not answer cannot keep the menu waiting. An update, *Restart session* after an update and `jaffer daemon stop` shut down plainly, and the conversation is offered again. Reset removes `~/.jaffer`, and with it the saved conversation: nothing is resumed afterwards, and a fresh Jaffer starts.
- **Print mode.** `claude -p` / `--print` (also clustered, as in `-cp`) answers once and is never a conversation to come back to: `isPrintMode` (a single-pass tokenizer; a `-p` inside a quoted prompt is a word of the prompt) makes the daemon forget the point whenever such a run ends, however it ended; the hooks of one that is still running note nothing (so a shell, a daemon or an update that goes while it runs leaves nothing to resume); and keys typed during it count toward a started shell line. Every helper that reads a command line (`isClaudeCommand`, `endsConversation`, `isPrintMode`, `isInteractiveCommand`) slices its input to the `COMMAND_HEAD` (4096-character) head itself, because the line comes from the shell's marks and can be forged at any length, and the window reads it too; timing tests feed them 1 MB and 8 MB crafted lines (unbounded patterns used to throw `RangeError` at about 8 MB).
- **Config.** `session.keepRunning` (false) and `session.stayAwake` (true) are conformed like every key: on load and on every patch a value takes the kind of its default (a section stays an object, a switch a boolean, a list a list of text), and one that does not fit keeps what was there. `jaffer config set` says when it refused a value. A change of `session.keepRunning` by any route (Settings, `jaffer service`, `jaffer config set`) makes the daemon reconcile the agent with every guard of the install policy, so the switch and the agent cannot disagree for a whole session. Keys the defaults no longer list (0.5.0's `session.autoResume`) stay in the file and nothing reads them.

## Memory

See the README for the lifecycle. Storage is plain files under `~/.jaffer/memory`: `items.jsonl` (source of truth), `skills.jsonl`, `journal.jsonl` (every mutation with before/after), `episodes/YYYY-MM-DD.jsonl` (raw, pruned after 45 days), generated `MEMORY.md` and per-skill markdown, and your `NOTES.md` / `POLICY.md`.

Ranking = confidence × time-decay (half-life per kind) × usage × scope relevance (global vs the project you are in) × BM25 match to the current request.

## Process boundaries and trust

The renderer is sandboxed (`contextIsolation`, no Node) and only reaches the daemon through the preload bridge; the main process checks the sender frame. Hook payloads and everything fed to memory or a model are redacted first.

- **The window shows one page.** `shared/window-policy.ts` (`isAppUrl`) is used by `will-navigate` and by the IPC sender check: a file dropped on the window, or a link, never navigates it to a page that would then get the preload bridge (and with it a shell to type into). The `reveal` IPC opens Jaffer's own folder only; `openExternal` takes http(s) only.
- **A program may copy, not read.** The terminal answers OSC 52 *write* requests (so `ssh` can fill the clipboard) but never a *read* request (`osc52Provider`): whatever you last copied is not for the program that printed the query.
- **The redactor is on the hot path.** It runs on the daemon's main thread over untrusted text (command output, transcripts), which also relays the terminal. Every rule is bounded (no unbounded run of characters before a literal); `test/redact.test.ts` holds timing tests, because one unbounded rule once took 10 s on 9 KB.
- **Files of the user's own** (`~/.claude/settings.json`, `~/.claude/CLAUDE.md`) are written through a symlink and keep their permissions (`writeFileAtomic(..., { preserve: true })`); only skills carrying Jaffer's marker line are ever removed from `~/.claude/skills`; `reset` refuses a folder that is a code checkout or holds none of Jaffer's own files.
- **What is kept on disk, unredacted:** the screen and scrollback of the session (`~/.jaffer/session/screen.json`, mode 0600) so that the session survives a reboot; it is your terminal's own content. `session.restoreScreen` (Settings → Appearance, on by default) turns it off: the file is deleted the moment it is switched off and never written, while the folder (`state.json`) is still restored. *Settings → Reset* removes it too. Beside it, `session/claude.json` holds the conversation Claude Code may be resumed from (an id, a folder, a time); it is cleared when the conversation ends on purpose, and *Reset* removes it. `~/Library/LaunchAgents/com.jafforge.jaffer.daemon.plist` and `~/.jaffer/bin/jafferd` exist only while the login-agent switch is on.

## Updates

`src/main/updates.ts` (`UpdateController`) drives `electron-updater` against the GitHub releases and decides nothing about the outside world itself: the updater, the dialog and ending the session are injected, so it is tested with fakes (`test/update-controller.test.ts`). `src/shared/update-policy.ts` holds the pure parts (prompt wording, when to ask, version checks, reading `codesign` output). The flow is check → download in the background → **ask** (native dialog) → on yes, end the session through the daemon (`app.shutdown`) and `quitAndInstall`. `autoInstallOnAppQuit` is off on purpose: quitting must never replace the app behind a running session. Only a packaged, Developer ID signed app checks (the bundle's signature is read at startup), only non-prerelease releases count, and errors are logged to `~/.jaffer/updater.log` and shown in Settings, never as a dialog unless the user asked. The release side is `scripts/release-mac.sh`: it checks `latest-mac.yml` and uploads it after everything it names.

## The window

The renderer is a terminal card on a canvas, with a thin title bar above (folder, branch, what is running, a Memory button) and, on demand, one drawer on the right: memory. Colours come from layered tokens derived from the active theme (`themes.ts`): `--chrome` is the canvas, `--surface` the card on it, `--raised` things on that. A theme change repaints the whole app.

- The title bar reads `session.info` (folder, branch) and keeps itself live from `pty.start`, `pty.command` and `pty.cwd` events. The ring beside the folder is `processBadge` (`src/shared/process-badge.ts`): an ordinary command spins while it runs; Claude Code spins only while its hooks say it is working. The tint under it is `shared/danger-zone.ts` (`dangerZone`: an `ssh` or `mosh` command line names the host, otherwise the branch is matched against `safety.protectedBranches` with plain `*` globs, never regular expressions); it is a static `data-danger` attribute and a box-shadow, so it needs no motion setting and shifts no layout.
- The companion (`Pet.tsx`, `src/shared/pet-mood.ts`) is an SVG in a corner of the terminal card, chosen in Settings → Appearance (`appearance.companion`, listed in `src/shared/companions.ts`; anything unknown is the mole). The mole is the original; the other five are scenes (below). The mole is an SVG in that corner. Every pose is a `[data-mood]` state (sleep, rest, dig, alert, cheer), so it is right with Animations off too; the motion is added only under `:root:not([data-motion='off'])` and stops under macOS Reduce motion. It ignores pointer events. A helper mole stands for each running subagent (`ClaudeSession.subagents`, at most three, `src/shared/pet-crew.ts`); a helper whose agent finished cheers for a moment and leaves. Effort grows with time (`src/shared/pet-effort.ts`: 30 s, 2 min, 5 min since the turn or the command started, or since the helper's own `SubagentStart`; `ClaudeSubagent.startedAt`, `info.busySince`): `data-effort` 0–3 sets the digging tempo (`--t`) and adds the sweat drop, the hard hat and a bigger pile, all static under Animations off. Background agents outlive the turn that started them, so `Stop` does not end them: `SubagentStop`, the session ending, or half an hour of silence does.
- The scenes (`Scenes.tsx`, geometry in `src/shared/scene-geometry.ts`): **Matrix** (digital rain, an agent is a brighter coloured column), **Agent network** (a hub and up to three nodes passing packets), **Warp** (a starfield at speed, a wingman ship per agent), **Radar** (a sweep and a blip per agent) and **Reactor core** (counter-rotating rings, equaliser bars, satellites). They take the same inputs as the mole (`petMood`, effort, the crew from `pet-crew.ts`), draw into one 240×80 SVG frame, and follow the same rules: the still pose of every mood is the base style, motion is added only under `:root:not([data-motion='off'])` and ends at once under macOS Reduce motion, colours are theme tokens only (`--ok`, `--info`, `--violet`, `--accent`, `--warn`), and the corner ignores pointer events. Everything that varies (rain columns, star positions, node places) is a pure function in `scene-geometry.ts` with no randomness, so a render is the same every time and `test/scene-geometry.test.ts` can pin it. Settings shows each one live in a radio group (`CompanionPreview`); the effort tempo is the `--t` variable, as for the mole.
- Memory notices (`src/shared/memory-toast.ts`) interrupt only for something new learned or a memory the person asked for; housekeeping stays in the drawer's Activity log.
